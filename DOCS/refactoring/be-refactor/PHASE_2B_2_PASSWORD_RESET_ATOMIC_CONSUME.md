# 비밀번호 재설정 코드 원자적 소비

비밀번호 재설정 코드를 "조회 후 나중에 삭제"하던 것을, 조회와 동시에 삭제하는 `findAndRemove`로 바꿨습니다. 한 번만 써야 하는 코드로 비밀번호가 여러 번 바뀌지 않습니다.

## 이전과 현재

| 같은 코드로 20건 동시 재설정 | 이전 | 현재 |
| --- | --- | --- |
| 재설정 성공 | 여러 건 가능 | 1건 (나머지 19건은 이미 쓴 코드로 실패) |
| 남은 재설정 코드 | - | 0건 |
| 비밀번호 저장 방식 | 회원 문서 전체 저장 | `password` 필드만 `$set` |
| 재설정 중 바뀐 닉네임·rating | 이전 값으로 덮일 수 있음 | 유지 |
| 만료된 코드 | TTL 정리 전까지 남음 | 바로 소비 |

로컬 MongoDB 7.0.16에서 확인했습니다. 20건은 일회성 코드의 동시성 조건을 만들기 위한 횟수이며 처리량 측정이 아닙니다.

## 문제

```text
코드 조회 → 회원 문서 조회 → 새 비밀번호로 회원 전체 저장 → 코드 삭제
```

같은 코드로 동시에 요청하면 여러 요청이 조회를 통과했고, 각 요청이 비밀번호를 저장한 뒤 코드를 지우므로 비밀번호가 여러 번 바뀔 수 있었습니다. 비밀번호만 바꾸는데 회원 문서 전체를 저장해서, 그사이 바뀐 프로필이나 풀이 기록을 덮을 수도 있었습니다.

## 바꾼 내용

```text
새 비밀번호 정책 검사 → 코드 findAndRemove → 만료 확인 → 인코딩 → password 필드만 갱신
```

- 코드를 받은 요청 하나만 다음 단계로 갑니다.
- 비밀번호 갱신은 `_id` 조건 `updateFirst`와 `$set`이고, `matchedCount`로 회원 존재를 확인합니다.
- 코드 소비와 비밀번호 갱신은 다른 문서라 트랜잭션으로 묶지 않았습니다. 대신 소비한 코드는 이후 실패해도 되살리지 않아 재사용을 막습니다.
- 실제 발급 경로에서 쓰지 않던 Redis 재설정 코드 저장소는 지우고, API 설명을 실제 저장 방식(MongoDB 유일 인덱스와 TTL)에 맞췄습니다.

| 상황 | 코드 | 비밀번호 |
| --- | --- | --- |
| 새 비밀번호가 정책 위반 | 유지 | 변경 없음 |
| 만료된 코드 | 소비 | 변경 없음 |
| 코드의 회원이 없음 | 소비 | 변경 없음 |
| 정상 | 소비 | `password`만 변경 |

## 확인한 방법

- MongoDB 계약 테스트 6개가 20건 동시 재설정, 만료 코드, 정책 위반, 회원 없음, 인코딩 실패를 확인합니다.
- 인코딩을 멈춰 둔 사이 rating을 바꾸는 경합 테스트에서 새 비밀번호와 새 rating이 함께 남았습니다.
- `./gradlew clean check`가 통과했습니다(단위 503개, 통합 74개 중 67개 통과·조건부 7개 제외).

## 남은 한계

- 회원별로 활성 코드를 하나로 제한하는 작업은 [재설정 코드 발급 정합성](./PHASE_2B_3_PASSWORD_RESET_ISSUANCE_CONSISTENCY.md)에서 했습니다.
- 소비 뒤 인코딩이나 DB 갱신이 실패하면 코드는 없어지므로 사용자가 다시 발급받아야 합니다.

# 관리자 회원 조회 DB 페이징

관리자 회원 조회가 전체 회원을 앱으로 가져와 검색·필터·페이지 분할을 하던 것을, MongoDB 조건 조회로 옮겼습니다. 앱이 읽는 회원 수가 페이지 크기로 줄었습니다.

## 이전과 현재

| 회원 1,000명, 첫 페이지 20명 | 이전 | 현재 |
| --- | ---: | ---: |
| 앱이 읽어 변환한 회원 | 1,000 | 20 (98.0% 감소) |
| MongoDB 조회 | 3 | 3 |
| 응답 회원 수 | 20 | 20 |
| `totalElements` | 1,000 | 1,000 |
| 범위 밖 페이지 요청 | `IllegalArgumentException` | 빈 목록, `totalElements` 1,000 |
| `rating DESC` 정렬 요청 | 실제 정렬에 반영 안 됨 | MongoDB 정렬에 반영 |

로컬 MongoDB 7.0.16에서 새 컨테이너로 5회 반복했고 결과가 모두 같았습니다. 98.0%는 앱이 변환한 엔티티 수의 감소이며, 메모리·네트워크·응답 시간이 98% 줄었다는 뜻은 아닙니다.

## 문제

```text
students findAll → 메모리에서 검색·가입일 필터 → subList → 현재 페이지 회고 수 집계
```

회원이 많아질수록 한 페이지를 보려고 전체 회원 문서를 읽고 변환했습니다.

## 바꾼 내용

```text
students count(조건) → students find(조건 + 정렬 + skip + limit) → 현재 페이지 회고 수 집계
```

- 검색: `nickname`, `bojId`, `email` 중 하나에 대소문자 무시 부분 일치. 정규식 특수문자는 일반 문자로 처리합니다.
- 가입일: 시작일 00:00:00 이상, 종료일 23:59:59 이하.
- 정렬: 요청 정렬 뒤 `_id ASC`를 붙여 같은 값끼리도 페이지 순서가 고정됩니다.
- 결과가 없거나 범위 밖 페이지면 페이지 조회와 회고 집계를 건너뜁니다.

`$facet` 한 번으로 목록과 개수를 함께 받을 수도 있지만, 페이지 크기 상한이 없고 회원 문서에 풀이 기록이 들어 있어 16MB 문서 한도에 걸릴 수 있습니다. 그래서 `count`와 `find`를 따로 실행합니다.

## 확인한 방법

- 대소문자 무시 검색, `.`·`+` 같은 특수문자, 검색과 가입일 조건의 AND 결합을 확인합니다.
- `rating DESC, _id ASC` 동점 페이징, `createdAt`이 없는 기존 문서 호환을 확인합니다.
- `./gradlew clean check`가 통과했습니다(단위 485개, 통합 45개 중 38개 통과·조건부 7개 제외).

## 남은 한계

- `students`에 정렬용 인덱스가 없어 `count`와 `find`가 각각 전체를 검사합니다. 회원 12명 기준 검사 문서가 12개에서 24개로 늘었습니다. 정렬 인덱스는 [관리자 회원 정렬 인덱스](./PHASE_1D_ADMIN_RATING_INDEX.md)에서 추가했습니다.
- `count`와 `find`가 서로 다른 시점의 데이터를 볼 수 있습니다.
- 가입일 필터 인덱스, 부분 문자열 검색 전략, 페이지 크기 상한은 정하지 않았습니다.

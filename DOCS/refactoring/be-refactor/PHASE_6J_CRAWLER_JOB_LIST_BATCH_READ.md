# 문제 수집 작업 목록 일괄 조회

작업 목록을 볼 때 작업 수만큼 Redis를 호출하던 것을 `MGET` 한 번으로 묶었습니다. 만료된 작업의 정리 명령도 한 번에 보냅니다.

## 이전과 현재

| 조건 | 이전 Redis 명령 | 현재 Redis 명령 | 감소 |
| --- | ---: | ---: | ---: |
| 작업 1건 | 2회 | 2회 | 0% |
| 작업 5건 | 6회 | 2회 | 66.67% |
| 작업 20건 | 21회 | 2회 | 90.48% |
| 정상 20건 + 만료·손상 2건 | 27회 | 5회 | 81.48% |

로컬 Redis 7.2.5에 같은 데이터를 넣고, 목록 조회 중에 실행된 명령만 세었습니다. 명령 횟수 비교이며 응답 시간이나 전송량 개선율은 아닙니다.

## 문제

목록 조회는 작업 ID를 모두 읽은 뒤 상태를 하나씩 가져왔습니다.

```text
ZREVRANGE problem:job:index
GET problem:job:status:{jobId}  (작업 수만큼 반복)
```

반복 횟수는 화면 페이지 크기가 아니라 남아 있는 전체 작업 수였습니다. 페이지가 20건이어도 작업이 더 많으면 `GET`이 그만큼 늘었고, 이 흐름을 작업 목록, 감사 목록, 운영 지표, 대기 순번 계산이 함께 썼습니다. 만료되거나 읽을 수 없는 작업도 하나씩 `ZREM`, `DEL`로 지웠습니다.

## 바꾼 내용

상태 키를 목록 순서대로 만들어 `MGET` 한 번으로 읽고, ID와 결과를 같은 위치끼리 묶습니다.

```text
ZREVRANGE problem:job:index
MGET problem:job:status:{id1} ... {idN}
```

`MGET`의 빈 값은 "키 없음"과 "문자열이 아님"을 구분하지 못해서, 빈 값이 있을 때만 `TYPE`으로 확인합니다.

- 키가 없으면 만료된 작업으로 보고 정리 대상에 넣습니다.
- 그사이 새로 생긴 상태는 한 번 더 읽어서 지우지 않습니다.
- 문자열이 아닌 키는 건드리지 않고 409를 돌려줍니다.
- JSON을 읽을 수 없는 값은 정리 대상에 넣습니다.

정리 대상은 모아서 `ZREM` 한 번, `DEL` 한 번으로 지웁니다. 응답 형식과 API는 바꾸지 않았습니다.

## 확인한 방법

- 변경 전 조회 흐름을 테스트 안에 그대로 옮겨 두고, 같은 Redis와 같은 데이터에서 이전 흐름과 현재 서비스를 차례로 호출해 명령을 셌습니다.
- 작업 1·5·20건에서 이전과 현재의 페이지 응답, 정렬, 대기 순번이 같았습니다.
- 만료·손상 작업은 응답에서 빠지고, 정상 작업의 상태와 실패 기록은 남았습니다.
- 전용 MongoDB·Redis에 연결한 `./gradlew clean check`가 통과했습니다. 단위 테스트는 736개에서 738개로, 통과한 통합 테스트는 208개에서 215개로 늘었습니다.

```bash
./gradlew integrationTest --tests '*ProblemCollectorJobListQueryIntegrationTest'
```

## 남은 한계

- 명령 수는 줄었지만 `MGET`은 여전히 상태 N개를 모두 읽고, 서버도 모두 역직렬화합니다. 전송량과 CPU 비용은 작업 수에 비례합니다.
- 상태·기간 필터와 페이징은 전체를 읽은 뒤 서버에서 처리합니다.
- 목록 index에는 만료 시간이 없어서, 만료된 항목은 목록을 읽을 때 정리됩니다.
- 여러 키를 읽는 `MGET`은 단일 Redis 기준입니다.

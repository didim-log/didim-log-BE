# AI 사용량 원자적 예약

AI 리뷰 사용량을 "조회 후 성공하면 증가"에서 "호출 전에 Redis에서 한 번에 예약, 실패하면 반환"으로 바꿨습니다. 동시에 요청이 몰려도 사용자·전역 한도를 넘지 않습니다.

## 이전과 현재

| 20건 동시 요청 | 이전 | 현재 |
| --- | ---: | ---: |
| 같은 사용자, 남은 한도 1 | 20건 모두 허용, 카운터 20 | 1건 성공, 19건 사용자 한도로 거절 |
| 서로 다른 사용자, 남은 전역 한도 1 | 확인과 증가가 분리돼 막지 못함 | 1건 성공, 19건 전역 한도로 거절 |
| 같은 예약을 두 번 반환 | - | 한 번만 감소, 원래 값으로 복구 |
| 서비스 비활성 상태 | 조회에서 거절 | 거절, 카운터 생성 0건 |

로컬 Redis 7.2.5에서 확인했습니다. 이전 코드는 모든 요청이 조회를 끝낸 뒤 증가하도록 순서를 맞춰 경쟁을 재현했습니다. 한도 정합성 비교이며 응답 시간은 재지 않았습니다.

## 문제

AI 리뷰는 사용 가능 여부를 먼저 읽고, 외부 AI 호출이 성공한 뒤에 카운터를 올렸습니다.

```text
사용량 조회 → 로그별 잠금 → 비동기 작업 등록 → AI 호출 성공 → 사용량 증가
```

잠금은 로그별이라 같은 사용자가 다른 로그에서 동시에 요청하면 함께 검사를 통과했고, 증가가 AI 호출 뒤라 그사이 요청은 반영 전 값을 읽었습니다. 전역·사용자 증가는 pipeline으로 묶었지만, pipeline은 한도 확인과 증가를 하나의 원자 연산으로 만들지 않습니다.

## 바꾼 내용

### 잠금 뒤 예약

동기·비동기 모두 로그 잠금을 먼저 얻고 사용량을 예약합니다. 비동기 요청은 실행 대기열에 넣기 전에 예약을 끝냅니다.

`reserveUsage`는 Lua 한 번으로 처리합니다.

```text
서비스 활성 확인 → 전역 한도 → 사용자 한도 → 예약 키 생성 → 두 카운터 증가 → 자정 만료 설정
```

예약 객체는 그날의 키를 들고 있어서, 자정을 넘겨 실패를 처리해도 다음 날 카운터를 줄이지 않습니다.

### 실패하면 반환

`releaseUsage`도 Lua 한 번으로, 예약 키가 있을 때만 지우고 두 카운터를 한 번씩 줄입니다. 같은 예약을 두 번 반환해도 한 번만 줄고, 카운터가 손상됐으면 아무것도 바꾸지 않습니다.

예약을 반환하는 경우는 실행기가 작업을 거절했을 때와 프롬프트 준비나 AI 호출이 실패했을 때입니다. AI 호출이 성공한 뒤 저장이 실패하면 사용량은 남깁니다. 반환 자체가 실패해도 원래 예외를 바꾸지 않고 로그만 남깁니다.

## 확인한 방법

- 실제 Redis 통합 테스트 6개가 사용자 한도, 전역 한도, 중복 반환, 비활성 상태, 손상된 카운터(`1.5`)를 확인합니다.
- 리뷰 서비스 단위 테스트 4개가 공급자 실패, 실행기 거절, 예약 거절, 성공 뒤 저장 실패에서의 사용량을 확인합니다.
- `AiUsageService`의 테스트 범위가 Line 4.20%에서 60.57%로 늘었습니다.
- 전용 MongoDB·Redis에 연결한 `./gradlew clean check`가 통과했습니다(단위 684개, 통합 167개 중 159개 통과·조건부 8개 제외).

- 여러 키를 쓰는 Lua는 단일 Redis 기준입니다.

# Phase 5A — AI 사용량 원자적 예약

## 문제

AI 리뷰 요청은 사용 가능 여부를 먼저 읽고, 외부 AI 호출이 성공한 뒤 전역·사용자
카운터를 증가시켰다.

```text
사용량 조회
→ 로그별 잠금
→ 비동기 작업 등록
→ AI 호출 성공
→ 전역·사용자 사용량 증가
```

로그 잠금은 `logId`별이므로 같은 사용자가 서로 다른 로그에서 요청하면 사용량
검사를 함께 통과할 수 있었다. 증가 시점도 비동기 대기열과 AI 호출 뒤여서 그
사이에 들어온 요청은 아직 반영되지 않은 카운터를 읽었다.

변경 전 코드에서 사용자 한도를 1로 두고 20개 스레드가 모두 검사를 마친 뒤
증가하도록 맞춘 기준선은 20개 요청을 모두 허용했고 사용자 카운터도 20이 됐다.
전역·사용자 증가는 Redis pipeline에 함께 넣었지만, pipeline은 한도 확인과 두
증가를 하나의 원자 연산으로 만들지 않는다.

## 유지한 사용량 정책

- `studentId`가 없는 이전 로그의 동기 호출은 기존처럼 사용량에 포함하지 않는다.
- 정상 처리 경로에서는 외부 AI 호출이 성공한 요청만 사용량으로 남긴다.
- 비동기 실행기 등록 실패와 외부 AI 호출 실패는 예약을 반환한다.
- 외부 AI 호출이 성공한 뒤 결과 저장이나 코드 캐시 저장이 실패해도 사용량은
  유지한다.
- 캐시 결과와 짧은 코드는 로그 잠금과 사용량 예약 전에 반환한다.

## 변경

### 로그 잠금 뒤 사용량 예약

동기·비동기 경로 모두 로그 잠금을 먼저 얻고 사용량을 예약한다. 잠금을 얻지 못한
요청은 이미 진행 중인 결과를 반환하며 사용량을 건드리지 않는다.

비동기 요청은 실행기 대기열에 넣기 전에 예약을 마친다. 작업 등록 시점에는
전역·사용자 한도가 함께 반영되며, 실행기나 공급자 호출이 실패하면 이후 반환된다.

### Redis Lua 원자 연산

`reserveUsage`는 Lua 한 번으로 다음 순서를 처리한다.

```text
서비스 활성 상태 확인
→ 전역 한도 확인
→ 사용자 한도 확인
→ 고유 예약 키 생성
→ 전역·사용자 카운터 반영
→ 세 키의 자정 TTL 설정
```

판정 순서는 기존과 같은 비활성, 전역 한도, 사용자 한도 순이다. 날짜와 자정까지
남은 시간을 같은 `LocalDateTime`에서 계산하고 밀리초 TTL을 사용한다. 예약 객체는
예약 당시의 전역·사용자 키를 보관하므로 자정을 지난 실패 처리도 다음 날
카운터를 줄이지 않는다.

카운터는 쓰기 전에 정수 형식으로 읽는다. `1.5`처럼 정수 형식이 아닌 값은 0으로
해석한 뒤 계산값을 직접 저장한다. 예약 키를 만든 뒤 `INCR`가 실패해 일부 값만
남는 경로를 없앴다.

### 실패 예약 반환

`releaseUsage`도 Lua 한 번으로 처리한다.

```text
예약 키 존재 확인
→ 전역·사용자 카운터 형식 확인
→ 예약 키 삭제
→ 두 카운터를 한 번만 감소
```

예약 키가 이미 없으면 `false`를 반환하므로 같은 예약을 두 번 반환해도 카운터는
한 번만 감소한다. 카운터가 손상된 경우에는 예약 키를 지우기 전에 중단해 두
카운터 중 일부만 감소하는 상태를 막았다.

리뷰 서비스는 다음 두 경우에 예약을 반환한다.

- 실행기가 작업 등록을 거절한 경우
- 프롬프트 준비 또는 외부 AI 호출이 실패한 경우

예약 반환을 위한 Redis 연산이 실패해도 원래의 작업 등록·AI 호출 예외를 바꾸지
않고 오류 로그를 남긴다.

## 정확성 비교

- Before SHA: `03c3792e67904abe6ffc6df57b7f230dfa2f5ff7`
- After code SHA: `cbcef8f153ad121984c1f665027a1f1b79be411e`
- Redis: `redis:7.2.5-alpine`
- 동시 요청: 20개
- 단일 JVM의 `AiUsageService` 객체: 4개

| 검증 | Before | After |
| --- | ---: | ---: |
| 같은 사용자·남은 한도 1 | 허용 20건 | 성공 1건·사용자 한도 거절 19건 |
| 서로 다른 사용자·남은 전역 한도 1 | 확인·증가 분리 | 성공 1건·전역 한도 거절 19건 |
| 사용자 카운터 | 한도 1에서 최종 20 | 한도 5에서 사전 4·최종 5 |
| 전역 카운터 | 요청별 후행 증가 | 사전 4·최종 5 |
| 같은 예약 2회 반환 | 별도 예약 없음 | `true` 1회·`false` 1회, 원래 값 복구 |
| 서비스 비활성 | 조회에서 거절 | 거절하며 전역·사용자 카운터 생성 0건 |

Before는 기존의 조회와 증가 사이 경쟁을 확정하기 위해 모든 스레드가 조회를 끝낸
뒤 증가하도록 맞췄다. After는 실제 Redis에서 20개 `reserveUsage`를 동시에
실행했다. 이 표는 요청 한도 정합성 비교이며 응답 시간이나 처리량 비교가 아니다.

추가로 실제 Redis에서 다음 손상 경계를 확인했다.

- `1.5` 카운터를 예약 전에 0으로 정규화하고 두 카운터를 1로 저장
- 예약 뒤 카운터가 손상되면 예약 키를 소비하지 않고 반환 중단
- 카운터를 복구한 뒤 같은 예약 반환 성공
- 사용량 키에 양수 TTL 설정

## 남은 제한

- 여러 키를 사용하는 Lua는 현재 단일 Redis 구성을 기준으로 한다. Redis Cluster로
  전환하면 같은 hash slot을 사용하도록 키 규칙을 함께 바꿔야 한다.
- 작업이 실행기에 등록된 뒤 프로세스가 종료되면 실패 반환 코드를 실행할 수 없다.
  이 예약은 당일 자정 TTL까지 보수적으로 사용량을 차지한다.
- 성공한 요청의 예약 키도 당일 자정에 만료된다. 생성 수는 전역 일일 한도로
  제한된다.
- 실패 예약 반환 중 Redis를 사용할 수 없으면 카운터는 자정까지 남을 수 있다.
- 공급자 자체 RPM·RPD 제한과 `GeminiRateLimiter`의 다중 명령 처리는 이번 단계의
  범위가 아니다.
- EC2 배포와 운영 Redis 상태 확인은 범위에서 제외했다.

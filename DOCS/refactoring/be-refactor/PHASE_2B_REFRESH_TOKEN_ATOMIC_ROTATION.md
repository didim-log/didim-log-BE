# Refresh Token 원자적 회전

Refresh Token 교체를 "조회 후 삭제 후 저장"에서 Redis Lua 한 번으로 바꿨습니다. 같은 토큰으로 동시에 갱신을 요청해도 새 토큰은 하나만 나갑니다.

## 이전과 현재

| 상황 | 이전 | 현재 |
| --- | --- | --- |
| 같은 토큰으로 20건 동시 갱신 | 여러 요청이 조회를 통과해 모두 새 토큰을 받을 수 있음 | 성공 1건, 실패 19건 |
| 갱신 뒤 남은 기존 토큰 키 | - | 0건 |
| 같은 사용자의 다른 기기 토큰 | - | 유지 |
| 갱신과 전체 폐기가 겹침 (20회 반복) | 토큰 키와 사용자별 Set이 어긋날 수 있음 | 두 순서 모두 남은 토큰 0건 |
| 같은 시각에 만든 두 토큰 | 문자열이 같아질 수 있음 (`jti` 없음) | 20개 연속 생성 모두 다름 |
| 정상 갱신 1건의 회원 조회 | 2회 | 1회 |

로컬 Redis 7.2.5와 MongoDB 7.0.16에서 확인했습니다. 20건, 20회는 동시성 조건을 만들기 위한 횟수이며 응답 시간 측정이 아닙니다.

## 문제

토큰 갱신은 Redis 조회와 삭제가 나뉘어 있었습니다.

```text
기존 토큰 조회 → 회원 조회 → 기존 토큰 삭제 → 새 토큰 저장
```

같은 토큰으로 요청이 동시에 오면 여러 요청이 조회를 통과해 모두 새 토큰을 받을 수 있었습니다. 토큰 저장, 사용자별 Set 갱신, 전체 폐기도 각각 여러 명령이라 서로 겹치면 토큰 키와 Set이 달라질 수 있었습니다. 토큰에 `jti`가 없어서 같은 사용자의 토큰을 같은 시각에 만들면 문자열이 같아질 수도 있었습니다.

## 바꾼 내용

Refresh JWT마다 무작위 `jti`를 넣고, 교체는 Lua 한 번으로 처리합니다.

```text
기존 토큰 조회 → 저장된 BOJ ID와 토큰 subject 비교 → 새 토큰 키 충돌 확인
→ 기존 키와 Set 멤버 삭제 → 새 키와 Set 멤버 저장 → 만료 시간 갱신
```

최초 로그인 저장(`save`)과 사용자 전체 폐기(`deleteByBojId`)도 Lua로 묶었습니다. 사용자별 Set 구조는 그대로라서 여러 기기의 토큰을 함께 쓸 수 있습니다. 조건이 맞지 않으면 아무 키도 바꾸지 않습니다.

서비스가 조회한 회원의 rating과 tier를 토큰과 함께 돌려줘서, 컨트롤러가 회원을 한 번 더 조회하지 않습니다.

## 확인한 방법

- 실제 Redis 계약 테스트 4개로 동시 교체, 교체와 전체 폐기 경합, subject 불일치, 새 키 충돌을 확인합니다.
- `./gradlew clean check`가 통과했습니다(단위 502개, 통합 68개 중 61개 통과·조건부 7개 제외).

## 남은 한계

- 세 키를 함께 다루는 Lua는 단일 Redis 기준입니다.
- 교체에 성공했는데 응답이 유실되면 클라이언트는 새 토큰을 모르므로 다시 로그인해야 합니다.
- 전체 폐기는 토큰 수만큼 Lua 안에서 지우므로, 로그아웃 API에 연결할 때 토큰 수 상한을 함께 봐야 합니다.

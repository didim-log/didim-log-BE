# Phase 2B — Refresh Token 원자적 회전

## 문제

기존 토큰 갱신은 Redis 조회와 삭제가 분리되어 있었다.

```text
기존 토큰 조회 → 회원 조회 → 기존 토큰 삭제 → 새 토큰 저장
```

같은 Refresh Token으로 요청이 동시에 들어오면 여러 요청이 조회를 통과해 모두 새
토큰을 받을 수 있었다. 토큰 저장과 사용자별 Set 갱신, 전체 폐기도 각각 여러 Redis
명령으로 실행되어 갱신과 폐기가 겹칠 때 정방향 키와 역방향 Set이 달라질 수 있었다.

Refresh Token에는 `jti`가 없었다. 같은 사용자의 토큰을 같은 시각에 만들면 토큰
문자열이 같아질 수 있어, 삭제한 키에 같은 토큰을 다시 저장할 가능성도 있었다.

## 변경

Refresh JWT마다 무작위 `jti`를 넣는다. 갱신 서비스는 서명된 토큰의 `subject`를
읽고 Redis 매핑과 먼저 비교해 이미 폐기된 토큰을 MongoDB 조회 전에 거절한다.
이 조회는 빠른 거절을 위한 것이며, 최종 교체 시 Lua가 같은 조건을 다시 확인한다.

교체 스크립트는 한 번의 Redis 실행에서 다음 순서를 처리한다.

```text
기존 토큰 조회
→ 저장된 BOJ ID와 서명 subject 비교
→ 새 토큰 키 충돌 확인
→ 기존 토큰 키와 사용자 Set 멤버 삭제
→ 새 토큰 키와 사용자 Set 멤버 저장
→ TTL 갱신
```

최초 로그인용 `save`와 사용자 전체 폐기용 `deleteByBojId`도 Lua로 묶었다. 사용자별
Set 구조는 그대로 유지하므로 여러 기기의 토큰을 함께 사용할 수 있다.

서비스에서 조회한 회원의 rating과 tier를 토큰과 함께 반환하도록 바꿨다. 컨트롤러의
두 번째 회원 조회가 없어져 정상 갱신 한 건의 MongoDB 회원 조회는 2회에서 1회로
줄었다.

## 동시 요청 결과

실제 Redis 7.2.5에 기존 토큰 한 개를 저장하고 20개 스레드가 서로 다른 새 토큰으로
동시에 교체를 요청했다.

| 확인 항목 | 결과 |
| --- | --- |
| 교체 성공 | 20건 중 1건 |
| 교체 실패 | 20건 중 19건 |
| 기존 토큰 키 | 0건 |
| 새 토큰 키 | 성공한 토큰 1건 |
| 같은 사용자의 다른 기기 토큰 | 유지 |
| 사용자별 Set | 다른 기기 토큰과 성공한 새 토큰만 유지 |

교체와 사용자 전체 폐기를 동시에 시작하는 검증도 20회 반복했다. Redis가 교체를 먼저
실행하면 전체 폐기가 새 토큰까지 지우고, 전체 폐기를 먼저 실행하면 교체가 기존 토큰
부재로 실패한다. 두 순서 모두 최종 토큰과 사용자별 Set은 남지 않았다.

저장된 BOJ ID와 서명 `subject`가 다르거나 새 토큰 키가 이미 있으면 교체를 거절하고
기존 토큰, 새 토큰, 사용자별 Set을 변경하지 않는다.

## 검증

격리한 MongoDB 7.0.16과 Redis 7.2.5에서 다음 명령을 실행했다.

```bash
./gradlew clean check jacocoMergedReport jacocoFullMergedReport --no-daemon
```

| 항목 | 결과 |
| --- | --- |
| 단위 테스트 | 502개 통과 |
| 통합 테스트 | 68개 중 61개 통과, 외부 연동·성능 테스트 7개 제외 |
| 새 Redis 계약 테스트 | 4개 통과 |
| Refresh Token `jti` | 연속 생성 20개 모두 존재하고 중복 없음 |
| core-v1 JaCoCo | Line 80.88%, Branch 58.92%, Class 91.33% |
| full-v1 JaCoCo | Line 64.17%, Branch 45.28%, Class 75.70% |

이 단계는 지연 시간 개선률을 측정한 작업이 아니다. 표의 20건과 20회는 동시성 계약과
최종 상태를 확인하기 위한 조건이다.

## 남은 범위

- 현재 로컬·CI·배포 구성은 단일 Redis다. 세 키를 함께 다루는 Lua는 Redis Cluster의
  서로 다른 hash slot에서 실행할 수 없으므로 Cluster 전환 시 키 형식과 마이그레이션이
  필요하다.
- 사용자 전체 폐기는 사용자별 토큰 수만큼 Lua 안에서 키를 삭제한다. 실제 로그아웃
  API에 연결할 때 토큰 수 상한과 실행 시간을 함께 확인해야 한다.
- Redis 교체 성공 뒤 응답이 유실되면 클라이언트는 새 토큰을 알 수 없다. 이 경우
  재로그인이 필요하다.
- 비밀번호 재설정 코드의 일회성 소비는 다음 단계에서 별도로 처리한다.

# 관리자 회원 조회 최적화

관리자 회원 목록은 회원마다 회고를 따로 조회하고, 전체 회원을 앱으로 가져와 메모리에서 정렬·페이지 분할을 했습니다. 네 단계에 걸쳐 조회 횟수, 앱이 읽는 회원 수, DB가 검사하는 문서 수를 줄였습니다.

## 이전과 현재

| 단계 | 조건 | 이전 | 현재 |
| --- | --- | --- | --- |
| [N+1 제거](./PHASE_1A_ADMIN_N_PLUS_ONE.md) | 회원 12명, 10명 페이지 | MongoDB 조회 11회 | 2회 (81.8% 감소) |
| [회고 studentId 인덱스](./PHASE_1B_RETROSPECTIVE_STUDENT_INDEX.md) | 같은 조건 | 회고 문서 12개 검사 (`COLLSCAN`) | 0개 (`IXSCAN`) |
| [DB 페이징](./PHASE_1C_ADMIN_DB_PAGINATION.md) | 회원 1,000명, 20명 페이지 | 앱이 회원 1,000명 변환 | 20명 (98.0% 감소) |
| [정렬 인덱스](./PHASE_1D_ADMIN_RATING_INDEX.md) | 같은 조건 | 페이지 조회가 문서 1,000개 검사 + 메모리 정렬 | 20개, 메모리 정렬 없음 (98.0% 감소) |
| 정렬 인덱스 | 같은 조건 | 페이지 + 개수 조회 검사 문서 2,000개 | 1,020개 (49.0% 감소) |

모두 로컬 MongoDB 7.0.16 합성 데이터에서 같은 단계의 변경 전후를 같은 조건으로 비교한 값입니다. 1B~1D는 새 컨테이너에서 5회씩 반복해 결과가 모두 같았습니다. 조회 횟수, 변환한 엔티티 수, 검사한 문서 수의 감소이며 응답 시간·처리량·메모리 개선율이 아닙니다.

## 측정 기준

- [테스트·커버리지 기준선](./PHASE_0A_COVERAGE_BASELINE.md): 전체 코드 범위 커버리지와 하락 방지 기준
- [성능 측정 환경 기준선](./PHASE_0B_PERFORMANCE_ENVIRONMENT.md): 이미지, JVM, 데이터, 반복 조건 고정
- [리팩터링 전 기준선 측정 결과](./PHASE_0B_BASELINE_RESULTS.md): 페이지 크기 1·5·10에서 조회 2·6·11회, 두 컬렉션 모두 `_id` 외 인덱스 없음

## 쓰지 않은 수치

- 10명 페이지 조회 11회 → 3회(72.7%)는 1A 이전과 1C 이후를 이어 붙인 값이라 대표 수치로 쓰지 않습니다. 1C는 `count`를 따로 실행해 1B 직후보다 조회가 1회 늘었습니다.
- 예전 README의 수집 시작 응답 `121 ms`는 측정 방법과 원본 결과가 없어 쓰지 않습니다.
- 2026-06-21 로컬 k6 결과는 JVM 힙 기록이 없고 이 단계들과 같은 전후 조건이 아니라 비교에 쓰지 않습니다.

## 확인한 방법

```bash
ADMIN_QUERY_BASELINE_RUN_ID=admin-query-verification performance/query/run-baseline.sh
./gradlew clean check --no-daemon
```

각 단계의 변경 전후 코드에서 위 스크립트를 실행하면 조회 횟수와 `explain("executionStats")` 결과를 JSON으로 남깁니다. 원본 JSON은 Git에 올리지 않습니다. 1A~1D 동안 단위 테스트는 482개에서 485개, 통합 테스트는 27개에서 53개로 늘었고 커버리지 하락 기준은 매 단계 통과했습니다.

## 남은 한계

- 회원 개수 조회는 여전히 전체 문서를 검사하고, 깊은 페이지는 건너뛴 만큼 인덱스 키를 읽습니다.
- 개수 조회와 페이지 조회가 서로 다른 시점의 데이터를 볼 수 있습니다.
- 가입일 필터 인덱스, 세 필드 부분 문자열 검색 전략, 페이지 크기 상한은 없습니다.
- 응답 시간·처리량·힙 사용량과 운영 EC2의 인덱스 생성은 측정하지 않았습니다.

# 관리자 회원 조회 최적화 근거 개요

## 문서 범위

이 문서는 관리자 회원 조회 리팩터링의 기준선과 Phase 1A~1D 결과를 한곳에서
확인하기 위한 색인이다. 결과 표에는 같은 단계에서 고정된 조건으로 전후를 직접
비교한 수치만 넣었다.

- [Phase 0A — 테스트·커버리지 기준선](./PHASE_0A_COVERAGE_BASELINE.md)
- [Phase 0B — 성능 측정 환경 기준선](./PHASE_0B_PERFORMANCE_ENVIRONMENT.md)
- [Phase 0B — 리팩터링 전 기준선 결과](./PHASE_0B_BASELINE_RESULTS.md)
- [Phase 1A — 관리자 회원 조회 N+1 제거](./PHASE_1A_ADMIN_N_PLUS_ONE.md)
- [Phase 1B — 회고 `studentId` 인덱스 보장](./PHASE_1B_RETROSPECTIVE_STUDENT_INDEX.md)
- [Phase 1C — 관리자 회원 조회 DB 페이징](./PHASE_1C_ADMIN_DB_PAGINATION.md)
- [Phase 1D — 관리자 회원 정렬 인덱스](./PHASE_1D_ADMIN_RATING_INDEX.md)

`performance/results/*`는 Git에서 제외되며 이 저장소에는 역사적 원시 JSON이 없다.
따라서 저장소에 남은 근거는 위 결과 요약 문서와 재현 스크립트다. 수치를 독립적으로
확인하려면 기록된 SHA에서 스크립트를 다시 실행해 새 원시 결과를 만들어야 한다.

## 문제, 변경, 결과

1. Phase 0A는 단위·통합 테스트를 합친 JaCoCo 범위와 하락 방지 기준을 고정했다.
2. Phase 0B는 관리자 목록이 페이지 회원마다 회고를 다시 읽고, 두 컬렉션 모두
   `_id_` 이외의 인덱스가 없다는 기준선을 기록했다.
3. Phase 1A는 회원별 회고 조회를 현재 페이지 회원 ID의 일괄 집계 한 번으로 바꿨다.
4. Phase 1B는 회고의 `studentId` 인덱스를 시작 시 보장하고 집계를 커버드
   `IXSCAN`으로 전환했다.
5. Phase 1C는 전체 회원을 애플리케이션에서 필터링·정렬·분할하던 구조를 MongoDB의
   `count + find`로 바꿨다.
6. Phase 1D는 기본 `rating DESC, _id ASC` 정렬을 지원하는 복합 인덱스를 보장해
   페이지 조회의 전체 컬렉션 검사와 블로킹 정렬을 제거했다.

## 교차 단계 수치와 제외한 수치

`11 → 3`, 72.7%는 직접 전후 비교가 아니다. Phase 1A 이전의 페이지 크기 10
명령 수 11회와 Phase 1C 이후의 명령 수 3회를 이어 붙인 교차 단계 수치다.
Phase 1C 자체의 직접 비교는 `3 → 3`이다. 따라서 `11 → 3`은 대표 성과 수치로
사용하지 않는다.

README에 기록됐던 수집 시작 응답 `121 ms`는 측정 SHA, 반복 횟수, 측정 방법과
원시 결과가 없어 이 문서의 근거로 사용하지 않는다.

2026-06-21 로컬 k6 결과도 이 단계의 전후 비교에 사용하지 않는다. 해당 결과는
별도 SHA `677069bb5b31fb87ba9b4d8ee4c72f4d7df375bf`에서 한 번 실행한 역사적
스냅샷이며 JVM 힙이 기록되지 않았다. Phase 1A~1D의 관리자 조회 계측과 같은
전후 규약이 아니고 원시 JSON도 저장소에 없다.
이 SHA는 현재 원격 브랜치나 태그에서도 참조하지 않아 새 clone에서 재현 기준으로
사용할 수 없다.

## 역사적 테스트·JaCoCo 기록

아래 값은 각 문서에 기록된 당시 `./gradlew clean check --no-daemon` 결과다.
현재 브랜치의 테스트 결과나 운영 성능을 뜻하지 않는다. `core-v1`은 일부
애플리케이션 패키지, 수집기, UI와 인프라를 제외하므로 전체 서비스 범위가 아니다.
`full-v1`은 `com/didimlog/**`의 프로덕션 클래스를 포함하고 테스트 클래스만
제외한다.

Phase 0A에서 Phase 1D까지 단위 테스트는 `482 → 485`로 3개, 통합 테스트는
`27 → 53`으로 26개 늘었다. 같은 기간 `core-v1`은 줄 `+0.83%p`, 분기
`+2.84%p`, 클래스 `+0.15%p`, `full-v1`은 줄 `+0.70%p`, 분기 `+1.77%p`,
클래스 `+0.22%p` 변했다. 프로덕션 코드 분모도 함께 바뀌었으므로 커버리지
차이를 추가된 테스트만의 효과로 해석하지 않는다.

Phase 0A의 하락 방지 기준은 `core-v1` 줄 78%, 분기 55%, 클래스 90%와
`full-v1` 줄 61%, 분기 42%, 클래스 74%다. 이는 시작 하한이며 품질 목표나 성능
지표가 아니다.

## 재현 방법

1. 비교할 단계의 전·후 SHA를 별도 Git 작업 트리에 준비한다.
2. 두 작업 트리가 깨끗한 상태인지 확인한다.
3. 각 작업 트리에서 서로 다른 `ADMIN_QUERY_BASELINE_RUN_ID`로 다음 스크립트를
   실행한다.

   ```bash
   ADMIN_QUERY_BASELINE_RUN_ID=admin-query-verification \
     performance/query/run-baseline.sh
   ```

4. Phase 1A는 해당 문서에 기록된 각 SHA의 명령을 따른다. Phase 1B~1D는 단계
   문서와 같이 전후를 각각 5회 실행하고 실행별 JSON 해시와 값을 비교한다.
5. 테스트와 커버리지는 각 SHA에서 다음 명령으로 확인한다.

   ```bash
   ./gradlew clean check --no-daemon
   ```

6. 새 원시 JSON은 기본적으로 Git에 포함되지 않는다. 검토가 필요하면 실행 SHA,
   깨끗한 상태, MongoDB 이미지 다이제스트, fixture, 페이지 조건과 반복 번호를
   함께 보존한다.

정확한 작업 트리 경로, 실행 ID와 원시 결과 경로는 각 Phase 문서의 `재현` 절을
따른다.

## 남은 비용과 검증 범위

- 학생 count는 계속 `COLLSCAN`으로 전체 회원 문서를 검사한다.
- 깊은 페이지의 건너뛰기 비용은 인덱스 키 검사 수로 남는다.
- count와 페이지 조회가 별도 명령이므로 두 명령이 서로 다른 시점의 데이터를 볼
  수 있다.
- 가입일 필터에는 별도 인덱스를 적용하지 않았다.
- 세 필드의 대소문자 무시 부분 문자열 검색은 일반 B-tree 인덱스로 해결하지 않았다.
- 페이지 크기 상한이 없다.
- 새 인덱스는 저장 공간과 `rating` 변경 시 쓰기 비용을 추가한다.
- 큰 운영 컬렉션의 인덱스 생성 시간과 자원 사용량은 측정하지 않았다.
- 지연시간, 처리량, 힙, CPU와 네트워크 사용량은 같은 전후 규약으로 측정하지 않았다.
- 운영 데이터와 EC2에서 인덱스 생성·선택을 확인하지 않았다.

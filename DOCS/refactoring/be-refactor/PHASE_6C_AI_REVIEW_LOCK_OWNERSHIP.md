# AI 리뷰 잠금 소유권 분리

AI 리뷰 잠금에 버전 번호를 붙여, 잠금이 만료된 이전 요청이 나중에 끝나도 다음 요청의 상태를 덮어쓰지 못하게 바꿨습니다.

## 이전과 현재

A가 잠금을 잡고 늦어지는 사이 잠금이 만료되고 B가 다시 잡은 상황입니다.

| 상황 | 이전 | 현재 |
| --- | --- | --- |
| A가 늦게 완료 | A 리뷰 저장, B의 만료 시각 삭제 | A 갱신 0건, B 상태 유지 |
| A가 늦게 실패 | B 상태를 `FAILED`로 바꾸고 잠금 해제 | A 갱신 0건, B `IN_PROGRESS` 유지 |
| 만료 시각과 정확히 같은 시점 | 경계가 나뉘지 않음 | A 완료·실패·연장 0건, 새 잠금 획득 성공 |
| 소유권을 잃은 A의 결과 | 응답과 코드 캐시에 저장될 수 있음 | 캐시 저장 0건 |
| 실행 전에 소유권을 잃음 | 공급자 호출 가능 | 사용량 반환, 공급자 호출 0건 |

로컬 MongoDB 7.0.16에서 실제로 기다리지 않고 저장소에 넘기는 시각을 앞당겨 위 순서를 재현했습니다. 한 로그의 상태 정합성을 본 것이고 응답 시간은 재지 않았습니다.

## 문제

AI 리뷰 잠금은 `IN_PROGRESS` 상태와 만료 시각만 저장했고, 완료와 실패 처리는 로그 ID와 "리뷰가 아직 없음"만 확인했습니다.

```text
A 잠금 획득 → A 처리 지연, 잠금 만료 → B 잠금 획득 → A 완료 또는 실패
```

이 순서에서 A의 완료는 B가 작업 중인 로그에 A의 리뷰를 저장했고, A의 실패는 B를 `FAILED`로 바꿔 세 번째 요청까지 들어오게 했습니다. 저장을 막더라도 서비스가 A의 결과를 응답과 코드 캐시에 넣을 수 있어서, 저장소 조건만 바꾸는 것으로는 부족했습니다.

## 바꾼 내용

### 잡을 때마다 버전 증가

잠금을 잡을 때 `findAndModify`로 `aiReviewLockVersion`을 1 올리고, 서비스는 그 값을 완료·실패까지 들고 갑니다. 완료와 실패는 아래 조건을 모두 만족해야 저장됩니다.

```text
_id = logId
aiReview = null
aiReviewStatus = IN_PROGRESS
aiReviewLockVersion = 잡을 때 받은 버전
aiReviewLockExpiresAt > now
```

B가 다시 잡으면 버전이 바뀌므로 A는 어떤 상태도 쓸 수 없습니다. 기존 로그에 버전 필드가 없어도 첫 획득에서 `$inc`가 1로 만들어서 일괄 변환이 필요 없습니다.

### 실행 직전 잠금 연장

비동기 요청은 잠금을 잡은 뒤 실행 대기열에서 기다리므로, 작업을 시작하기 직전에 같은 버전이고 아직 만료되지 않았을 때만 만료 시각을 늘립니다. 연장에 실패하면 예약한 AI 사용량을 돌려놓고 공급자를 부르지 않습니다.

### 소유권을 잃은 결과 버리기

공급자 응답 뒤 현재 버전으로 완료하지 못하면 결과를 코드 캐시에 넣지 않습니다. 다른 요청이 이미 완료했으면 저장된 리뷰를 돌려주고, 아직 유효한 후속 작업이 있으면 생성 중으로, 둘 다 없으면 재시도 가능한 실패로 응답합니다.

## 확인한 방법

- 저장소 통합 테스트가 A와 B의 버전이 실제로 오르는지, A의 시도 뒤에도 B의 버전과 만료 시각이 그대로인지, 이어서 B의 완료가 성공하는지 확인합니다.
- 만료 시각 경계와 버전 필드가 없는 기존 문서도 실제 MongoDB에서 확인합니다.
- 서비스 단위 테스트가 사용량 반환과 이전 결과 미노출을 확인합니다.

## 남은 한계

- 공급자 호출 중에는 잠금을 주기적으로 연장하지 않습니다. 기본 Gemini 응답 제한(45초 미만)이 잠금 시간보다 짧지만, 설정을 바꾸거나 프로세스가 오래 멈추면 외부 호출 비용이 중복될 수 있습니다. 이때도 오래된 결과의 저장과 캐시는 막힙니다.
- 이전 버전은 잠금 버전을 확인하지 않아서 섞어 돌리지 않고 한 번에 교체해야 합니다.

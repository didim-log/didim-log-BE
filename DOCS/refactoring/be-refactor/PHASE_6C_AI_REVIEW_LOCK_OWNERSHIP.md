# Phase 6C — AI 리뷰 잠금 소유권 분리

## 문제

AI 리뷰 잠금은 `IN_PROGRESS` 상태와 만료 시각만 저장했다. 완료와 실패 처리는 로그
ID와 `aiReview == null`만 확인했다.

```text
A 잠금 획득
→ A 처리 지연, 잠금 만료
→ B 잠금 재획득
→ A 완료 또는 실패 처리
```

이 순서에서 A의 완료 처리는 B가 작업 중인 로그에 A의 리뷰를 저장하고 B의 만료
시각을 지울 수 있었다. A가 늦게 실패하면 B의 상태를 `FAILED`로 바꾸고 잠금을
지워 세 번째 요청까지 들어올 수 있었다.

실제 MongoDB에서 논리 시각을 전진시켜 이 순서를 실행한 기준선은 A의 완료와 실패
처리를 모두 허용했다. 완료 저장이 거절되더라도 서비스는 A가 생성한 리뷰를 응답과
코드 캐시에 넣을 수 있어 저장소 조건만 바꾸는 것으로는 부족했다.

## 변경

### 획득할 때 잠금 버전 증가

`findAndModify`로 잠금을 획득할 때 `aiReviewLockVersion`을 1씩 증가시킨다. 저장소는
획득 뒤의 버전을 `AiReviewLock`으로 반환하고, 서비스는 사용량 예약부터 완료·실패
처리까지 같은 잠금 값을 전달한다.

완료와 실패 갱신은 다음 조건을 모두 확인한다.

```text
_id = logId
aiReview = null
aiReviewStatus = IN_PROGRESS
aiReviewLockVersion = acquiredVersion
aiReviewLockExpiresAt > now
```

A의 만료 뒤 B가 재획득하면 버전이 바뀌므로 A의 완료와 실패는 문서를 수정하지
못한다. B가 아직 재획득하지 않았더라도 만료된 A는 종료 상태를 기록할 수 없다.
B의 작업만 유효한 버전과 만료 시각으로 종료 상태를 기록할 수 있다. 버전은 종료
뒤에도 남겨 다음 획득에서 계속 증가시키고, 만료 시각만 제거한다.

기존 문서에 `aiReviewLockVersion`이 없어도 MongoDB의 `$inc`가 첫 획득에서 값을
`1`로 만든다. 별도 일괄 갱신 없이 기존 로그와 새 로그에 같은 규칙을 적용한다.

### 비동기 실행 직전 잠금 갱신

비동기 요청은 잠금을 잡은 뒤 실행기 대기열에 들어간다. 대기 시간이 lease에
포함되므로 작업을 시작하기 직전에 다음 조건으로 만료 시각을 갱신한다.

- 같은 잠금 버전
- `IN_PROGRESS`
- 리뷰가 아직 없음
- 기존 만료 시각이 현재보다 뒤

이미 만료됐거나 다른 요청이 재획득한 잠금은 다시 살리지 않는다. 갱신에 실패하면
예약한 AI 사용량을 반환하고 공급자를 호출하지 않는다.

### 소유권을 잃은 결과 차단

공급자 호출 뒤 현재 버전으로 완료하지 못하면 생성 결과를 코드 캐시에 저장하지
않는다. 현재 로그를 한 번 조회해 다른 작업이 이미 완료했다면 저장된 리뷰를
반환한다. 리뷰가 없을 때는 잃어버린 잠금보다 버전이 크고, 상태가 `IN_PROGRESS`이며,
만료 시각이 남은 후속 작업만 생성 중으로 판단한다. 완료 결과와 유효한 후속 작업이
모두 없으면 재시도 가능한 생성 실패로 처리한다. 이전 작업의 결과가 DB 밖의 캐시로
다시 노출되는 경로도 함께 막았다.

## 정확성 검증

- Before SHA: `a706c21cea3a29c3f5ee2a1bb5fdd461ecd38c43`
- MongoDB: `7.0.16`
- 시간 진행: 실제 대기 없이 저장소 인자의 논리 시각 사용

| 검증 | Before | After |
| --- | --- | --- |
| A 만료 → B 재획득 → A 완료 | A 리뷰 저장·B 만료 시각 제거 | A 갱신 0건·B 상태와 만료 시각 유지 |
| A 만료 → B 재획득 → A 실패 | B 상태를 `FAILED`로 변경 | A 갱신 0건·B `IN_PROGRESS` 유지 |
| `now == expiresAt` 경계 | A 종료·갱신과 새 획득의 경계가 분리되지 않음 | A 완료·실패·연장 0건, 새 잠금 획득 성공 |
| B 종료 처리 | A가 먼저 상태를 바꿀 수 있음 | B 버전으로 완료·실패 처리 성공 |
| 실행 전 lease 갱신 | 소유권 확인 없음 | 만료된 A 갱신 실패·유효한 B 갱신 성공·같은 만료 시각도 소유권 확인 성공 |
| 완료 전 소유권 상실 | A 리뷰 응답·코드 캐시 저장 가능 | A 리뷰 캐시 0건·후속 작업 유무에 맞는 응답 |
| 실행 전 소유권 상실 | 공급자 호출 가능 | 사용량 반환·공급자 호출 0건 |
| 버전 필드가 없는 기존 로그 | 잠금 소유자 구분 없음 | 첫 획득에서 버전 `1` 저장 |

저장소 통합 테스트는 A와 B의 버전이 실제로 증가하는지, A의 갱신 뒤 B의 버전과
만료 시각이 그대로인지, 이어서 B의 종료 처리가 성공하는지까지 확인한다. 또한
후속 획득 전 만료 경계와 버전 필드가 없는 원시 MongoDB 문서도 검사한다. 서비스
단위 테스트는 사용량 반환 정책과 이전 작업 결과 미노출을 확인한다.

이 단계는 한 로그의 상태 정합성 검증이다. 응답 시간이나 처리량을 비교하지 않아
성능 향상률은 기록하지 않았다.

## 남은 제한

- 공급자 호출 중에는 lease를 주기적으로 갱신하지 않는다. 기본 Gemini 연결·응답
  제한은 45초 lease보다 짧지만 설정 변경이나 긴 프로세스 정지가 있으면 외부 호출
  비용은 중복될 수 있다. 이 경우에도 잠금 버전 조건이 오래된 DB·캐시 반영은 막는다.
- 구 버전 애플리케이션은 잠금 버전을 확인하지 않는다. 구 작업을 종료한 뒤 새
  버전으로 전체 교체해야 하며, 구·신 버전을 함께 실행하는 순차 배포는 지원하지
  않는다.
- `aiReviewLockVersion`은 로그별 `Long` 값이다. 현실적인 획득 횟수에서는 범위를
  넘지 않지만 별도 초기화는 하지 않는다.
- Gemini 전체 요청 간격과 RPM·RPD 제한의 Redis 원자 처리는 다음 단계로 분리한다.
- EC2 배포와 운영 데이터 전환은 이번 검증 범위에서 제외했다.

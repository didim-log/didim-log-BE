# 관리자 피드백 작성자 일괄 조회

관리자 피드백 목록에서 작성자를 행마다 따로 조회하던 것을, 페이지의 작성자 ID를 모아 한 번에 조회하도록 바꿨습니다.

## 이전과 현재

| 페이지 크기 | 이전 학생 조회 | 현재 학생 조회 | 이전 전체 읽기 | 현재 전체 읽기 | 감소 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1회 | 1회 | 3회 | 3회 | 0% |
| 5 | 5회 | 1회 | 7회 | 3회 | 57.14% |
| 20 (기본) | 20회 | 1회 | 22회 | 3회 | 86.36% |

전체 읽기는 피드백 개수 조회 1회, 페이지 조회 1회, 학생 조회를 더한 값입니다. 로컬 MongoDB 7.0.16에 같은 데이터를 넣고 MongoDB 명령 수를 센 결과이며, 응답 시간이나 DB CPU 개선율은 아닙니다.

## 문제

피드백 페이지를 읽은 뒤 각 행의 작성자를 다시 조회했습니다.

```kotlin
feedbacks.map { feedback ->
    studentRepository.findById(feedback.writerId)
}
```

기본 페이지 20건이면 학생 조회가 20번 더 나갔고, 같은 작성자가 여러 번 나와도 행마다 조회했습니다. 응답에 쓰지 않는 비밀번호나 풀이 기록 같은 필드도 함께 읽었습니다.

## 바꾼 내용

현재 페이지의 작성자 ID를 중복 없이 모아 학생의 `_id`와 `bojId`만 한 번에 읽습니다.

```text
filter:     { _id: { $in: [현재 페이지 작성자 ID] } }
projection: { _id: 1, bojId: 1 }
```

- 탈퇴해서 학생 문서가 없는 작성자도 피드백 행과 `writerId`는 그대로 두고 `bojId`만 `null`로 응답합니다.
- 빈 페이지에서는 학생 조회를 하지 않습니다.
- 피드백 상태 변경 API는 한 건만 조회하므로 바꾸지 않았습니다.

페이지 20건의 실행 계획은 `_id_` 인덱스를 쓰는 `IXSCAN`이었고, 요청한 ID 20개 중 있는 학생 19건만 읽었습니다.

## 확인한 방법

- 변경 전 조회 흐름을 테스트 안에 그대로 두고, 같은 데이터에서 이전 흐름과 현재 컨트롤러를 차례로 호출해 MongoDB 명령을 셌습니다.
- 피드백 21건, 첫 페이지 작성자 20명(BOJ 연동 18명, 미연동 1명, 탈퇴 1명) 조건에서 페이지 크기 1·5·20 모두 이전과 현재 응답의 모든 필드가 같았습니다.
- 전용 MongoDB·Redis에 연결한 `./gradlew clean check`가 통과했습니다(단위 736개, 통합 217개 중 208개 통과·조건부 9개 제외).

## 남은 한계

- 피드백 개수 조회와 페이지 조회 2회는 그대로입니다.
- 정렬(`createdAt DESC`)의 인덱스 사용과 관리자 목록의 최대 페이지 크기는 따로 정해야 합니다.
- 응답 시간, DB CPU, 전송량은 재지 않았습니다.

# Phase 3C — 계정 삭제 경로 통합과 연관 데이터 정리

## 문제

본인 탈퇴와 관리자 강제 탈퇴가 서로 다른 코드를 사용했다. 본인 탈퇴는 회고와
피드백을 함께 지웠지만 관리자 삭제는 Student만 지워 같은 계정에 대해 결과가
달랐다. 두 경로 모두 사용자 로그, 커스텀 템플릿과 비밀번호 재설정 코드를 남겼다.

관리자 강제 탈퇴를 나타내는 `USER_DELETE` 감사 유형은 선언돼 있었지만 실제 삭제
API에서 기록하지 않았다. 삭제 API 문서에도 같은 학생의 상태 변경 작업과 겹쳤을 때
반환하는 `409`, Redis를 사용할 수 없을 때의 `503`이 빠져 있었다.

## 삭제 정책

| 데이터 | 소유자 키 | 처리 |
| --- | --- | --- |
| Refresh Token | Redis의 학생 ID 역색인 | 삭제 |
| 비밀번호 재설정 코드 | `studentId` | 삭제 |
| 회고 | `studentId` | 삭제 |
| 피드백 | `writerId` | 삭제 |
| 커스텀 템플릿 | `studentId` | 삭제 |
| 풀이 로그 | `studentId` | 삭제 |
| Student | `_id` | 마지막에 삭제 |
| 시스템 템플릿 | 소유자 없음 | 보존 |
| 관리자 감사 로그 | 관리자 식별자 | 보존 |
| `studentId`가 없는 이전 로그 | 안정적인 소유자 없음 | 보존 |

BOJ ID는 변경하거나 나중에 다른 계정이 사용할 수 있는 표시용 스냅샷이다. 따라서
`studentId`가 없는 이전 로그를 현재 BOJ ID만으로 계정 데이터라고 판단해 삭제하지
않는다.

## 변경

`AccountDeletionService`가 본인 탈퇴와 관리자 강제 탈퇴의 공통 흐름을 담당한다.

```text
학생 ID별 세션 잠금 획득
→ 잠금 안에서 Student 최신 조회
→ Refresh Token 전체 폐기
→ 비밀번호 재설정 코드 삭제
→ 회고·피드백·커스텀 템플릿·학생 ID가 있는 로그 삭제
→ Student를 ID로 마지막 삭제
```

- Refresh Token 폐기 중 Redis 저장소 오류가 나면 재시도 가능한
  `503 SESSION_STATE_UNAVAILABLE`로 변환하고 MongoDB 삭제를 시작하지 않는다.
- 하위 컬렉션 삭제가 중간에 실패하면 Student를 남긴다. 이미 끝난 삭제는 멱등
  연산이므로 같은 학생 ID로 다시 실행해 남은 데이터를 정리할 수 있다.
- MongoDB 여러 컬렉션과 Redis를 하나의 트랜잭션으로 묶었다고 표현하지 않는다.
  프로젝트에는 `MongoTransactionManager`가 없고 로컬 MongoDB도 단일 인스턴스다.
- 본인 탈퇴와 관리자 강제 탈퇴는 같은 서비스에 한 번만 위임한다.
- 관리자 삭제가 성공한 뒤 `USER_DELETE`와 대상 `studentId`, 요청 IP를 감사 로그로
  남긴다. 감사 저장은 기존 정책대로 비동기 최선 노력 방식이며, 실행 큐가 요청을
  거부해도 이미 끝난 삭제의 성공 응답을 바꾸지 않는다.

사용자별 삭제 조건이 컬렉션 전체 검사가 되지 않도록 다음 인덱스를 초기화기에
추가했다.

| 컬렉션 | 인덱스 |
| --- | --- |
| `feedbacks` | `{ writerId: 1 }` |
| `templates` | `{ studentId: 1 }` |

회고, 로그와 비밀번호 재설정 코드는 기존 `studentId` 선두 인덱스를 사용한다.

## API 계약

본인 탈퇴와 관리자 강제 탈퇴는 다음 실패 응답을 공통으로 문서화한다.

| 상황 | 응답 |
| --- | --- |
| 대상 Student 없음 | `404 STUDENT_NOT_FOUND` |
| 같은 학생의 계정 상태 변경 작업과 잠금 충돌 | `409 SESSION_STATE_CONFLICT` |
| 세션 상태 저장소 사용 불가 | `503 SESSION_STATE_UNAVAILABLE` |

동시에 들어온 삭제 두 건은 한 건이 성공하고 다른 한 건은 잠금 시점에 `409`가 될 수
있다. 첫 요청이 완료된 뒤 다시 요청하면 대상이 없으므로 `404`다.

## 검증

단위 테스트에서 다음을 확인했다.

- 세션 폐기, 하위 컬렉션, Student 순서
- Student가 없으면 세션·하위 데이터 삭제를 시작하지 않음
- 잠금 또는 Refresh Token 폐기 중 Redis 실패 시 `503`, MongoDB 삭제 0건
- 하위 컬렉션 삭제 중 실패하면 Student 보존
- 같은 요청 재시도로 남은 삭제 완료
- StudentService와 AdminService가 공통 삭제 흐름을 각각 한 번 호출
- 관리자 삭제 성공 시 `USER_DELETE` 감사 기록 1회, 실패 시 0회
- 감사 작업 제출이 거부돼도 완료된 관리자 삭제는 성공 응답 유지

MongoDB 7.0.16을 별도 로컬 컨테이너로 실행해 본인·관리자 서비스 경로를 각각
검증했다.

- 대상의 회고·피드백·학생 ID 로그·커스텀 템플릿·재설정 코드·Student 삭제
- 시스템 템플릿과 다른 학생의 모든 데이터 보존
- 같은 BOJ ID여도 안정적인 학생 ID가 없는 이전 로그 보존
- 삭제 도중 `documentVersion`이 바뀌어도 안정적인 Student ID로 마지막 삭제
- `feedbacks.writerId`, `templates.studentId` 인덱스 실제 생성

전체 `clean check`에서 단위 테스트 653개와 통합 테스트 146개를 실행했다. 단위
테스트는 모두 통과했고, 통합 테스트는 139개가 통과했으며 외부 Gemini·crawler
조건이 필요한 7개는 조건부 제외됐다. core-v1과 full-v1 JaCoCo 하한도 통과했다.
Line 커버리지는 core `83.94%`, full `69.13%`다. 직전 단계보다 각각 `0.13%p`,
`0.18%p` 증가해 README의 별도 커버리지 성과로 기록하지 않았다.

이 단계는 삭제 범위와 실패 경계를 검증한 작업이다. 반복 지연 시간이나 처리량을
측정하지 않았으므로 성능 향상률을 기록하지 않는다.

## 남은 범위

- 여러 MongoDB 컬렉션 삭제 중 프로세스가 중단되면 Student는 남지만 앞서 지운
  데이터는 이미 삭제된 상태다. 강한 전체 원자성이 필요하면 replica set 기반 탈퇴
  전용 트랜잭션이나 삭제 상태와 재시도를 관리하는 별도 흐름이 필요하다.
- 계정 삭제와 사용자 데이터 쓰기는 아직 모두 같은 잠금을 사용하지 않는다. 삭제
  전에 시작한 로그·피드백·템플릿 전체 저장이나 신규 회고 upsert가 삭제 뒤 늦게
  끝나면 고아 문서를 만들 수 있다. 다음 단계에서 사용자 소유 쓰기와 삭제가 같은
  생명주기 잠금을 사용하도록 바꾸고 실제 경합을 검증한다.
- 일일 AI 사용량 키와 OAuth 교환 코드는 학생 ID 역색인이 없고 짧은 TTL로 만료된다.
  계정 삭제 직후 물리 삭제하는 대상에는 포함하지 않는다.

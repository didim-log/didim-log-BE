# 추천 카테고리 단일 조회

문제 추천이 카테고리마다 따로 조회하던 것을 한 번의 조회로 합쳤습니다. 조회 경로마다 달랐던 난이도 조건도 하나로 맞췄습니다.

## 이전과 현재

| 항목 | 이전 | 현재 |
| --- | ---: | ---: |
| `BFS`·`RELATED` 추천 1회의 문제 조회 | 31회 | 1회 (96.77% 감소) |
| 학생 조회를 포함한 전체 조회 | 32회 | 2회 (93.75% 감소) |
| 추천 결과 | 4건 | 4건 (같은 문제) |
| 난이도 최솟값·최댓값과 같은 문제 | 대표 카테고리 조회에서 빠짐 | 포함 |
| `difficultyLevel`만 있는 이전 문서 | 빠지거나 매핑 예외 | 정상 변환 |

로컬 MongoDB 7.0.16에 문제 6건을 넣고 같은 요청(`category=BFS`, `filterMode=RELATED`, `count=50`)을 이전·현재 코드에 보내 명령 수를 센 결과입니다. 응답 시간이나 처리량은 재지 않았습니다.

## 문제

추천은 확장한 카테고리마다 `problems`를 따로 조회하고 마지막에 태그 조회 결과를 합쳤습니다. `BFS`를 기본 `RELATED` 모드로 요청하면 부모·형제 카테고리까지 30개가 만들어져 조회가 31번 나갔습니다.

난이도 조건도 경로마다 달랐습니다.

- 대표 카테고리 조회는 `level`만 보고 최솟값·최댓값을 제외했습니다.
- 태그 조회는 `level`이나 `difficultyLevel`을 보고 경계를 포함했습니다.
- `difficultyLevel`만 있는 이전 문서는 태그 조회에 잡힌 뒤 `level` 매핑에서 예외가 났습니다.

## 바꾼 내용

`RecommendationService`가 모드에 맞는 카테고리와 태그를 먼저 계산한 뒤 조회를 한 번만 합니다.

```text
유효 난이도 = level이 있으면 level, 없으면 difficultyLevel

유효 난이도 BETWEEN min AND max
AND (category IN 대상 카테고리 OR tags IN 확장 태그)
```

- `EXACT`는 확장 태그를 비워 카테고리 조건만 씁니다.
- 한 문제가 카테고리와 태그에 모두 맞아도 한 번만 나옵니다.
- `difficultyLevel`만 있는 문서는 읽을 때만 `level`로 바꿔 변환하고, 저장된 문서는 고치지 않습니다.
- 카테고리 확장 범위, 언어 필터, 이미 푼 문제 제외, 무작위 선택, 응답 필드는 그대로입니다.

## 확인한 방법

- 같은 측정 코드를 이전·현재 코드에 붙여 공개 서비스 메서드를 호출하고, 데이터를 넣은 뒤에 실행된 MongoDB 명령만 셌습니다. 결과는 문제 ID로 정렬해 비교했고 같았습니다.
- 변경 전 코드에서 경계 난이도 누락, `difficultyLevel` 문서 누락, 매핑 예외를 먼저 재현했습니다.
- 통합 테스트로 난이도 1·5 포함과 6 제외, 모드별 확장 범위, 중복 제거, 이전 난이도 필드 변환, 호출당 조회 2회를 확인합니다. 추천 저장소의 실제 MongoDB 통합 테스트는 0개에서 3개로 늘었습니다.
- 전용 MongoDB·Redis에 연결한 `./gradlew clean check`가 통과했습니다(단위 731개, 통합 208개 중 199개 통과·조건부 9개 제외).

```bash
./gradlew integrationTest --tests '*RecommendationQueryIntegrationTest'
./gradlew test --tests '*RecommendationServiceTest'
```

## 남은 한계

- `problems` 인덱스를 자동으로 만들지 않습니다. 조회 횟수는 줄었지만, 데이터가 많을 때 읽는 문서 수는 실행 계획으로 따로 확인해야 합니다.
- 후보를 모두 읽은 뒤 언어와 푼 문제를 걸러서, 후보 수만큼 메모리를 씁니다.
- 이전 난이도 필드는 읽을 때만 보정하고 저장 문서를 일괄 수정하지는 않았습니다.

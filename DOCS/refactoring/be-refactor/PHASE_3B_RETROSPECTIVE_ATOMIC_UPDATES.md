# 회고 원자 갱신과 풀이 기록 삭제 정합성

회고 수정·북마크·삭제가 문서를 읽고 전체를 다시 저장하던 것을, 필요한 필드만 한 번의 명령으로 바꾸도록 고쳤습니다. 회고 삭제 때 학생 문서 전체를 다시 쓰던 것도 풀이 관련 필드만 갱신합니다.

## 이전과 현재

| 상황 | 이전 | 현재 |
| --- | --- | --- |
| 회고 수정과 북마크를 동시에 | 이전 스냅샷이 다른 쪽 변경을 덮을 수 있음 | 두 변경 모두 보존 |
| 북마크를 두 요청이 동시에 토글 | 같은 값으로 두 번 저장될 수 있음 | 한 번씩 반영되어 원래 값으로 |
| 삭제 뒤 늦게 도착한 수정 | 같은 ID 회고가 다시 생길 수 있음 | 409, 다시 생기지 않음 |
| 회고 삭제 시 학생 문서 | 비밀번호·프로필까지 전체 저장 | 풀이 관련 4개 필드만 갱신 |
| 회고의 대표 카테고리 | 비어 있음 | 문제 카테고리 영문 표준명 저장 |
| 삭제의 MongoDB 명령 | 5회 | 4회 |

로컬 MongoDB 7.0.16 컨테이너에서 확인했습니다. 명령 수는 코드 경로 비교이며 응답 시간은 재지 않았습니다.

## 문제

회고 수정과 북마크는 문서를 읽은 뒤 `save`로 전체를 다시 썼습니다. 요청이 겹치면 이전 스냅샷이 먼저 반영된 필드를 덮었고, 삭제가 먼저 끝나면 늦은 저장이 같은 ID 문서를 다시 만들 수 있었습니다.

회고 삭제는 학생 문서 전체를 읽어 해당 문제 풀이를 빼고 다시 저장해서, 비밀번호나 프로필처럼 관계없는 필드까지 다른 요청과 경합했습니다. 회고의 `mainCategory`도 문제 카테고리와 연결되지 않아 카테고리 검색에 쓸 수 없었습니다.

## 바꾼 내용

### 작성과 수정

- 기존 회고는 `_id`와 소유자를 조건으로 `findAndModify(upsert=false)` 해서 본문, 요약, 풀이 정보, 카테고리만 바꿉니다. 그사이 삭제됐으면 다시 만들지 않고 409를 돌려줍니다.
- 새 회고는 `(studentId, problemId)` 유일 인덱스와 원자 upsert로 만들고, 인덱스 충돌이면 한 번 재시도합니다.
- 생성 시각과 북마크는 처음 만들 때만 정합니다.

### 북마크

서버에서 값을 뒤집어 저장하지 않고, aggregation update의 `$not`으로 현재 DB 값을 한 명령 안에서 뒤집습니다.

### 삭제

```text
회고 조회·소유권 확인
→ 학생 문서에서 그 문제 풀이를 빼고 마지막 풀이일·연속 일수 다시 계산
→ _id + documentVersion 조건으로 풀이 관련 필드만 갱신 (충돌 시 최대 3회 재시도)
→ _id + studentId 조건으로 회고 삭제
```

회고와 학생은 다른 문서이고 MongoDB 트랜잭션을 쓰지 않아서 두 변경을 한 번에 묶지는 못합니다. 학생 쪽을 먼저 정리해서, 중간에 장애가 나도 남은 회고로 삭제를 다시 시도할 수 있게 했습니다.

| 상황 | 응답 |
| --- | --- |
| 회고가 처음부터 없음 | 404 |
| 다른 학생의 회고 | 403 |
| 확인 뒤 대상이 사라짐, 충돌 반복 | 409, `retryable=true` |

## 확인한 방법

실제 MongoDB에서 다음을 확인했습니다.

- 북마크 동시 토글: 반환값 `true`, `false` 한 번씩, 최종 값은 처음 값
- 같은 학생·문제로 동시 최초 작성: 둘 다 완료, 문서 1건
- 같은 회고 재작성: ID, 생성 시각, 북마크 유지, 카테고리 검색으로 조회됨
- 수정 중 삭제가 먼저 끝남: 늦은 수정은 409, 회고 재생성 없음
- 같은 문제 풀이 2건과 다른 문제 1건이 있을 때 삭제: 그 문제 풀이만 제거, 비밀번호와 다른 풀이 유지, 버전 1 증가
- 삭제 도중 다른 문제 풀이 저장: 재시도 뒤 두 변경 모두 반영

전체 `./gradlew clean check`가 통과했습니다(단위 652개, 통합 146개 중 139개 통과·조건부 7개 제외).

## 남은 한계

- 학생 정리와 회고 삭제 사이에 프로세스가 멈추면 풀이만 먼저 빠진 상태가 남을 수 있습니다. 같은 삭제 요청을 다시 보내면 정리됩니다.
- 삭제 뒤 들어온 작성이나 풀이 제출은 새 기록으로 처리합니다. 삭제를 항상 우선하려면 삭제 상태(tombstone)가 따로 필요합니다.
- 보관 기간이 지난 회고를 지우는 작업은 회고만 지우고 풀이 기록은 남깁니다.

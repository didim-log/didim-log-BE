# Phase 3B — 회고 원자 갱신과 풀이 기록 삭제 정합성

## 문제

회고 수정과 북마크 변경은 문서를 읽은 뒤 `save`로 전체 문서를 다시 저장했다. 같은
회고에 요청이 겹치면 먼저 반영된 필드를 이전 스냅샷이 덮어쓸 수 있었고, 삭제가 먼저
끝난 뒤 늦은 저장이 같은 ID의 문서를 다시 만들 수도 있었다.

회고 삭제는 Student 전체를 읽어 해당 문제의 풀이를 뺀 뒤 다시 저장했다. 비밀번호,
프로필, 다른 문제의 풀이처럼 삭제와 관계없는 필드까지 쓰기 대상이 되므로 다른 요청과
경합할 범위가 컸다. 회고의 `mainCategory`도 문제 카테고리와 연결되지 않아 카테고리
검색에 사용할 값이 비어 있었다.

## 변경

### 작성과 수정

```text
학생·문제 확인
→ 같은 studentId + problemId 회고 조회
→ 기존 회고
   _id + studentId 조건 findAndModify, upsert=false
   본문·요약·풀이 정보·문제 카테고리만 $set
→ 신규 회고
   studentId + problemId 조건 findAndModify, upsert=true
   유일 인덱스 경합은 한 번 재시도
→ 대상 소멸 또는 반복 충돌은 409, retryable=true
```

- 기존 회고 갱신은 `_id`와 소유자를 조건에 함께 넣어 다른 사용자의 문서를 바꾸지
  않는다.
- `upsert=false`이므로 소유권 확인 뒤 삭제된 기존 회고가 같은 ID로 다시 생기지 않는다.
- 신규 회고는 `(studentId, problemId)` 유일 인덱스와 원자 upsert를 함께 사용한다.
- `createdAt`과 북마크는 신규 삽입에서만 설정하고, 재작성에서는 유지한다.
- `mainCategory`는 Problem의 `ProblemCategory.englishName`으로 저장한다.

### 북마크

북마크는 애플리케이션에서 이전 값을 뒤집어 전체 저장하지 않는다. MongoDB aggregation
update의 `$not`을 사용해 현재 DB 값을 한 명령 안에서 반전하고 변경된 문서를 반환한다.
두 요청이 동시에 시작해도 각각 한 번씩 반영된다.

### 사용자 삭제 API

```text
_id로 회고 조회·소유권 확인
→ Student 스냅샷에서 같은 problemId 풀이 전체 제거
→ 남은 풀이로 lastSolvedAt·consecutiveSolveDays 재계산
→ _id + documentVersion 조건 findAndModify
   solutions·lastSolvedAt·consecutiveSolveDays 갱신, documentVersion + 1
→ 충돌이면 최신 Student를 읽고 최대 3회 재계산
→ _id + studentId 조건으로 회고 findAndRemove
```

- Student 전체를 `save`하지 않고 풀이 상태 네 필드만 CAS로 갱신해 인증·프로필 필드를
  쓰기 대상에서 제외했다.
- 최신 또는 유일한 풀이를 제거하면 남은 풀이 날짜를 기준으로 마지막 풀이일과 연속
  풀이 일수를 다시 계산한다. 풀이가 없으면 각각 `null`, `0`으로 초기화한다.
- 풀이가 없더라도 Student가 존재하면 `documentVersion`을 증가시킨다. 삭제 전 Student
  스냅샷의 늦은 전체 저장과 Study CAS의 첫 시도는 이 버전 차이로 충돌한다.
- 소유권 확인 뒤 다른 요청이 회고를 먼저 삭제했다면, Student 정리까지 끝난 상태이므로
  최초 조회한 회고를 반환해 삭제를 성공으로 마친다.

회고와 Student는 서로 다른 MongoDB 문서이며 이 프로젝트에는 MongoDB 트랜잭션
관리자가 없다. 따라서 두 변경 전체를 하나의 원자 작업으로 표현하지 않는다. Student
정리를 먼저 실행해 두 번째 작업 전 장애가 나더라도 남아 있는 회고의 `problemId`로
삭제를 재시도할 수 있게 했다.

삭제 정상 경로의 MongoDB 명령 수는 다음과 같다.

| 경로 | Before | After |
| --- | ---: | ---: |
| Student 조회 | 2 | 1 |
| 회고 조회·소유권 확인 | 1 | 1 |
| Student 풀이 제거 | 1 | 1 |
| 회고 삭제 | 1 | 1 |
| 합계 | 5 | 4 |

이 표는 코드 경로의 명령 수 비교다. 지연 시간과 처리량을 반복 측정하지 않았으므로
성능 향상률로 환산하지 않는다.

## 충돌 응답

| 상황 | 응답 |
| --- | --- |
| 회고가 조회 시점부터 없음 | `404 RETROSPECTIVE_NOT_FOUND` |
| 회고가 다른 학생 소유 | `403 ACCESS_DENIED` |
| 소유권 확인 뒤 수정·토글 대상이 사라짐 | `409 RESOURCE_STATE_CONFLICT`, `retryable=true` |
| 신규 upsert의 유일 인덱스 충돌이 재시도 뒤에도 반복됨 | `409 RESOURCE_STATE_CONFLICT`, `retryable=true` |
| 삭제 중 Student가 사라짐 | `409 RESOURCE_STATE_CONFLICT`, `retryable=true` |

## 검증

MongoDB 7.0.16을 별도 로컬 컨테이너로 실행했다.

- 같은 회고의 북마크를 두 요청이 동시에 토글
  - 두 반환값은 `true`, `false`가 각각 한 번
  - 최종 상태는 처음 값인 `false`
- 같은 학생·문제로 두 요청이 동시에 최초 작성
  - 두 요청 모두 완료
  - 최종 문서 한 건
  - 본문과 요약은 한 요청의 값 묶음으로 저장
- 같은 회고를 다시 작성
  - ID와 생성 시각 유지
  - 기존 북마크 유지
  - 문제 카테고리를 영문 표준명으로 저장하고 카테고리 검색으로 다시 조회
- 회고 수정과 북마크 토글을 동시에 실행
  - 수정 필드와 북마크 변경 모두 보존
- 기존 회고 갱신을 소유권 확인 뒤 멈추고 삭제를 먼저 완료
  - 늦은 갱신은 재시도 가능한 409
  - 삭제된 ID와 같은 학생·문제의 회고가 다시 생기지 않음
- Student에 같은 문제 풀이 두 건과 다른 문제 풀이 한 건을 둔 뒤 회고 삭제
  - 같은 문제 풀이만 모두 제거
  - 다른 문제 풀이, 비밀번호, 평가·자격 증명 필드 유지
  - 남은 풀이 기준으로 마지막 풀이일과 연속 풀이 일수 재계산
  - `documentVersion` 정확히 1 증가
  - 삭제 전 Student 스냅샷의 전체 저장은 낙관적 잠금 충돌
- 유일한 풀이의 회고 삭제
  - 풀이 배열 비움
  - 마지막 풀이일 `null`, 연속 풀이 일수 `0`
- 삭제의 첫 Student CAS 직전에 다른 문제 풀이 저장
  - 첫 삭제 CAS 충돌 뒤 최신 Student 재조회
  - 동시에 저장한 다른 문제 풀이 보존
  - 대상 문제 풀이만 제거
  - 동시 풀이 저장과 삭제를 합쳐 `documentVersion` 2 증가

단위 테스트에서는 원자 저장소 호출, 유일 인덱스 충돌 재시도 한도, 삭제 CAS의
충돌 뒤 성공·4회 소진·저장소 오류 비재시도, 403·404·409 분기와 동시 삭제의 멱등
응답을 확인했다. Controller 테스트에서는 북마크 경합의
`409 RESOURCE_STATE_CONFLICT`와 `retryable=true` 응답을 확인했다.

전체 `clean check`에서 단위 테스트 652개와 통합 테스트 146개를 실행했다. 통합
테스트는 139개가 통과했고 외부 Gemini·crawler 조건이 필요한 7개는 조건부
제외됐다. core-v1과 full-v1 JaCoCo 하한도 통과했다. 직전 단계 대비 Line 커버리지는
core `83.52% → 83.81%`, full `68.72% → 68.95%`로 각각 `0.29%p`, `0.23%p`
증가해 README의 별도 커버리지 성과로 기록하지 않았다.

## 남은 범위

- Student 풀이 제거와 회고 삭제 사이에 프로세스가 중단되면 풀이만 먼저 제거된 상태가
  남을 수 있다. 같은 삭제 요청을 재시도하면 남은 회고를 삭제할 수 있다.
- 삭제가 끝난 뒤 들어온 신규 작성은 새 회고로 처리한다. 삭제와 겹친 모든 작성보다
  삭제가 반드시 우선해야 한다면 tombstone이나 삭제 상태가 별도로 필요하다.
- 삭제와 겹친 풀이 제출은 이전 문서 버전의 첫 CAS가 실패하지만, StudyService가 최신
  Student를 읽어 재시도하면 풀이가 다시 추가될 수 있다. 이는 삭제 뒤 제출로 처리하며,
  풀이에도 삭제 우선 정책이 필요하면 별도 삭제 상태가 필요하다.
- 회고와 연결할 식별자가 없는 Log는 회고 삭제 대상이 아니다.
- 보관 기간이 지난 회고를 지우는 `RetrospectiveCleanupService`는 회고 문서만 일괄
  삭제하며 Student 풀이 기록을 제거하지 않는다. 보관 정리와 사용자 삭제 API의 정책
  통합은 별도 범위다.
- 이 단계는 정합성과 코드 경로의 명령 수를 검증했다. 운영 지연 시간이나 처리량
  개선 수치는 기록하지 않는다.

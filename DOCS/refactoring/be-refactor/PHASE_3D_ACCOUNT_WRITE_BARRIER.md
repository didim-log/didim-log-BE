# 계정 삭제와 사용자 데이터 쓰기 경합 차단

계정 삭제가 진행되는 동안 같은 학생의 데이터 쓰기가 끼어들지 못하게, 인증에서 쓰던 학생별 Redis 잠금을 사용자 데이터 쓰기에도 적용했습니다. 삭제된 계정의 데이터가 늦게 다시 생기지 않습니다.

## 이전과 현재

| 상황 | 이전 | 현재 |
| --- | --- | --- |
| 삭제 중 신규 회고 작성 | 삭제 뒤 고아 회고가 생길 수 있음 | 409, 삭제 완료 뒤 재시도하면 404, 고아 회고 0건 |
| 템플릿 저장 중 계정 삭제 | 삭제된 템플릿이 다시 저장될 수 있음 | 삭제가 409, 재시도하면 둘 다 정리 |
| 로그·피드백·템플릿의 늦은 `save` | 지워진 문서를 다시 만듦 | 최신 회원 확인 뒤에만 저장 |
| 삭제 뒤 끝난 OAuth 교환·가입 토큰 발급 | 쓸 수 없는 Refresh Token이 Redis에 남음 | 최신 회원 확인 뒤에만 발급 |
| 로그 AI 피드백 저장 | 로그 전체를 다시 써서 AI 리뷰 필드를 덮을 수 있음 | 피드백 두 필드만 부분 갱신 |

로컬 MongoDB 7.0.16과 Redis 7.2.5에서 위 경합을 재현해 확인했습니다.

## 문제

[계정 삭제 경로 통합](./PHASE_3C_ACCOUNT_DELETION_CONSISTENCY.md)으로 두 탈퇴 경로가 같은 정리를 하게 했지만, 삭제 전에 시작한 요청이 삭제 뒤에 저장되는 경우가 남아 있었습니다.

- 신규 회고는 upsert라서 회원이 지워진 뒤 고아 회고를 만들 수 있었습니다.
- 로그, 피드백, 사용자 템플릿은 버전 없는 `save`라서 지워진 문서를 다시 만들 수 있었습니다.
- OAuth 코드 교환이나 가입의 토큰 발급이 삭제 뒤에 끝나면 Refresh Token이 남았습니다.

## 바꾼 내용

### 같은 잠금 하나

인증에서 쓰던 학생별 Redis 잠금(`credential:session:lock:{studentId}`)을 그대로 씁니다. 공통 부모 `StudentLifecycleCoordinator`를 더했지만 키와 구현은 하나라서, 인증·계정 삭제·데이터 쓰기가 서로 다른 잠금을 잡는 일이 없습니다.

```text
학생별 잠금 획득 → 잠금 안에서 회원 최신 조회 → 대상 문서 조회와 소유권 확인 → 짧은 쓰기 → 해제
```

잠금은 기다리지 않습니다. 같은 학생의 작업이 이미 실행 중이면 409 `SESSION_STATE_CONFLICT`로 바로 거절하고, 요청자가 잠시 뒤 다시 시도합니다.

| 영역 | 잠그는 쓰기 |
| --- | --- |
| 계정 | 본인·관리자 삭제 |
| 로그 | 생성, AI 리뷰 피드백 |
| 고객 피드백 | 생성, 상태 변경, 삭제 |
| 템플릿 | 생성, 수정, 삭제, 기본값 설정 |
| 회고 | 작성, 수정, 북마크, 삭제 |
| 인증·가입 | Refresh Token 회전, OAuth 교환, 가입 뒤 토큰 발급 |

### 부분 갱신

- 로그 AI 피드백은 `_id`와 회원 ID를 조건으로 `aiFeedbackStatus`, `aiFeedbackReason`만 `findAndModify(upsert=false)` 합니다. 문서가 이미 지워졌으면 다시 만들지 않고, AI 리뷰 본문은 그대로 둡니다.
- 기본 템플릿 설정은 회원 문서 전체 대신 해당 필드만 바꾸고 버전을 올립니다.

### 잠그지 않은 쓰기

풀이 결과 저장은 이미 버전 조건 갱신과 재시도로 보호되고 있어서 잠그지 않았습니다. 잠그면 같은 학생의 정상적인 동시 제출 중 하나가 바로 409가 됩니다. solved.ac 프로필 동기화, 비밀번호·프로필 부분 갱신, `@Version`이 있는 회원 저장도 삭제된 문서를 다시 만들지 않아 그대로 두었습니다.

## 확인한 방법

- 실제 MongoDB·Redis에서 템플릿 생성 중 삭제 409, 삭제 중 회고 작성 409와 재시도 404, 인증 잠금과 같은 키로 충돌, 부분 갱신 뒤 다른 필드 보존을 확인했습니다.
- 단위 테스트로 모든 쓰기가 회원 재조회 뒤에만 저장하는지, 잠금 충돌 시 저장·토큰 발급 0건인지, 공개 경계에서 잠금을 한 번만 잡는지 확인합니다.
- 전체 `./gradlew clean check`가 통과했습니다. 단위 테스트는 653개에서 665개로, 통합 테스트는 146개에서 151개로 늘었습니다(144개 통과·조건부 7개 제외).

## 남은 한계

- 잠금은 30초 lease를 갱신하는 방식입니다. 프로세스 중단이나 긴 네트워크 단절로 잠금을 잃는 경우까지 막으려면 tombstone이나 fencing token이 필요합니다.
- MongoDB와 Redis는 하나의 트랜잭션이 아니어서, 이미 반영된 쓰기를 되돌리지는 않습니다.
- OAuth 교환 코드는 회원 ID를 알기 위해 먼저 소비하므로, 잠금이 충돌하면 OAuth 로그인을 다시 시작해야 합니다.

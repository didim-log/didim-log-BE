# 가입·회고 데이터 정합성

가입과 회고 저장의 중복 방지를 애플리케이션 검사에만 맡기지 않고, MongoDB 유일 인덱스를 시작 시점에 확실히 만들도록 바꿨습니다.

## 이전과 현재

| 항목 | 이전 | 현재 |
| --- | --- | --- |
| 로그인 제공자 ID, BOJ ID, 이메일, 닉네임 중복 | 조회 후 저장이라 동시 요청은 둘 다 통과 가능 | 유일 인덱스가 중복 저장 거부 |
| 같은 학생·문제 회고 두 스레드 동시 저장 | 2건이 생길 수 있음 | 1건 |
| 엔티티의 인덱스 선언 | 자동 생성이 꺼져 있어 실제로 없을 수 있음 | 시작 시 확인하고 없으면 생성 |
| 비밀번호 재설정 코드 만료 | 인덱스 없음 | 만료 시각 TTL 인덱스 |
| 기존 데이터에 중복이 있을 때 | - | 데이터를 지우지 않고 시작 중단 |

## 문제

가입과 회고 저장은 중복을 먼저 조회한 뒤 저장했습니다. 같은 값으로 동시에 요청하면 두 요청이 모두 조회를 통과할 수 있어서 애플리케이션 검사만으로는 유일성을 보장할 수 없었습니다.

엔티티에 인덱스 어노테이션은 있었지만 자동 생성이 꺼져 있었고, 시작 시 `MongoIndexInitializer`는 관리자 조회용 인덱스 두 개만 만들었습니다. 그래서 위 조건들은 실제 DB 규칙이 아니었습니다.

## 바꾼 내용

시작할 때 아래 인덱스를 확인하고 없을 때만 만듭니다.

| 컬렉션 | 키 | 옵션 |
| --- | --- | --- |
| `students` | `provider`, `providerId` | unique |
| `students` | `nickname` | unique |
| `students` | `bojId` | 문자열 값에만 적용하는 partial unique |
| `students` | `email` | 문자열 값에만 적용하는 partial unique |
| `retrospectives` | `studentId`, `problemId` | unique |
| `password_reset_codes` | `resetCode` | unique |
| `password_reset_codes` | `expiresAt` | TTL (`expireAfter=0`) |

이메일과 BOJ ID를 partial 인덱스로 둔 것은, 두 값이 없는 소셜 계정을 여러 개 저장할 수 있게 하기 위해서입니다. 기존 데이터에 중복이 있거나 같은 이름의 인덱스 옵션이 다르면 데이터를 건드리지 않고 시작을 멈춥니다.

함께 BOJ 인증을 거친 일반 가입은 `isVerified=true`로 저장하고, 회고 보관 기간 설정을 서비스가 실제로 읽는 경로(`app.retrospective.retention-days`)로 옮겼습니다.

## 확인한 방법

MongoDB 계약 테스트 9개가 매번 별도 DB를 만들어 확인합니다.

- 학생 식별자 네 가지의 중복 저장 거부
- 이메일·BOJ ID가 없는 학생 여러 명 저장
- 같은 학생·문제 회고를 두 스레드에서 동시에 넣으면 최종 1건
- 중복 회고가 이미 있으면 두 문서를 그대로 두고 인덱스 초기화 실패
- 재설정 코드의 unique·TTL 인덱스 옵션

`./gradlew clean check`가 통과했습니다(단위 500개, 통합 64개 중 57개 통과·조건부 7개 제외).

## 남은 한계

- 이메일은 저장된 문자열 그대로 비교합니다. 대소문자와 공백까지 같은 계정으로 보려면 정규화와 기존 데이터 변환이 필요합니다.
- TTL 삭제는 MongoDB 백그라운드 작업이라 만료 직후 삭제를 보장하지 않아서, 비밀번호 변경 때도 만료 검사를 계속합니다.
- 인덱스는 하나씩 만들기 때문에 중간에 실패하면 앞서 만든 인덱스는 남습니다. 운영 반영 전에 중복과 옵션을 먼저 점검해야 합니다.

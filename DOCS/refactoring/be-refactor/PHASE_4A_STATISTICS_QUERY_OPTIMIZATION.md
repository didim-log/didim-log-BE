# 통계 조회 데이터 축소

통계 API가 쓰지도 않는 회고 본문까지 읽던 것을 필요한 필드만 읽도록 바꾸고, 연도별 히트맵은 날짜 범위를 MongoDB 조회 조건과 인덱스로 옮겼습니다.

## 이전과 현재

| 조회 | 항목 | 이전 | 현재 |
| --- | --- | ---: | ---: |
| 전체 통계 | 돌려받는 회고 크기 | 5,230,680 B | 107,790 B (97.94% 감소) |
| 전체 통계 | 읽은 문서 수 | 1,200 | 1,200 |
| 2024년 히트맵 | 돌려받는 회고 | 1,200건 | 366건 |
| 2024년 히트맵 | 돌려받는 회고 크기 | 5,230,680 B | 18,396 B (99.65% 감소) |
| 2024년 히트맵 | 읽은 문서 수 | 1,200 | 366 (69.50% 감소) |
| 2024년 히트맵 | 사용한 인덱스 | `studentId` | `studentId + createdAt` |
| 두 조회 | 통계 결과 | - | 이전과 같음 |

로컬 MongoDB 7.0.16에 한 학생의 회고 1,200건(본문 4,096자)과 다른 학생 회고 120건을 넣고, 이전·현재 코드를 각각 5번 실행한 결과입니다. MongoDB가 돌려준 문서 크기와 실행 계획을 비교한 것이며 API 응답 시간은 재지 않았습니다.

## 문제

`GET /api/v1/statistics`는 집계에 쓰지 않는 회고 본문(최대 5,000자)까지 문서 전체를 읽었습니다. 회고가 늘수록 MongoDB에서 서버로 넘어오는 데이터와 객체 생성 비용이 같이 커졌습니다.

연도별 히트맵은 학생의 회고를 전부 읽은 뒤 서버에서 그 해만 골랐습니다. `(studentId, createdAt)` 인덱스 선언은 있었지만 자동 인덱스 생성이 꺼져 있어 실제로 만들어진다는 보장이 없었습니다.

## 바꾼 내용

### 필요한 필드만 읽기

전체 통계는 `problemId`, `createdAt`, `solutionResult`, `solvedCategory` 네 필드만 `RetrospectiveStatisticsView`로 받습니다. 회고 수, 실패 수, 카테고리 분포, 최근 365일 히트맵 계산식은 그대로입니다.

### 연도 범위를 조회 조건으로

```text
studentId = 요청 사용자
createdAt >= 그 해 1월 1일 00:00
createdAt <  다음 해 1월 1일 00:00 (올해면 내일 00:00)
```

끝 시각을 "미만"으로 둬서 12월 31일의 소수점 이하 시각도 빠지지 않습니다. 히트맵은 `problemId`, `createdAt`만 읽습니다. 미래 연도는 학생 존재만 확인하고 빈 목록을 돌려줍니다.

### 인덱스 보장

`MongoIndexInitializer`가 서버 시작 시 `retrospectives`에 `{ studentId: 1, createdAt: -1 }` 인덱스(`idx_retro_student_created`)를 반복 실행해도 안전하게 만듭니다. 기존 `studentId` 단일 인덱스는 다른 조회를 위해 남겼습니다.

## 확인한 방법

- 이전·현재 코드에서 같은 측정 코드를 돌려 공개 `StatisticsService`가 실제로 보낸 조회 조건과 projection을 잡고, 같은 조회를 다시 실행해 문서 크기를 더하고 `explain("executionStats")`로 실행 계획을 확인했습니다.
- 날짜, 문제 ID, 카테고리 순서를 맞춰 비교한 통계 결과는 두 조회 모두 이전과 같았습니다.
- 서비스 특성화 테스트 5개와 실제 MongoDB 범위·projection 테스트 2개를 더해 결과 유형, 카테고리 분리, 연도 경계, 다른 학생 제외, 인덱스 옵션을 확인합니다.
- 전용 MongoDB·Redis에 연결한 `./gradlew clean check`가 통과했습니다(단위 680개, 통합 159개 중 151개 통과·조건부 8개 제외).

```bash
performance/statistics/run-baseline.sh
```

## 남은 한계

- 전체 통계는 모든 회고를 집계해야 해서 읽는 문서 수는 그대로입니다. 회고가 더 많아지면 MongoDB 집계나 사전 집계를 비교해야 합니다.
- 새 인덱스만큼 저장 공간과 회고 저장 시 인덱스 갱신 비용이 늘어납니다.
- `createdAt`이 없는 과거 문서는 연도 조회에서 빠집니다.

# Phase 5B — 문제 상세·언어 부분 갱신

## 문제

상세 수집 작업은 처리 대상을 먼저 조회한 뒤 BOJ 응답을 기존 `Problem`에 복사해
전체 문서를 저장했다.

```text
상세가 없는 Problem 조회
→ BOJ 상세 크롤링
→ 조회한 Problem에 상세 복사
→ 전체 문서 저장
```

크롤링 중 solved.ac 메타데이터 작업이 같은 문제의 제목, 난이도, 분류나 태그를
갱신하면 늦게 끝난 상세 작업이 오래된 값으로 되돌릴 수 있었다. 상세 새로고침과
언어 갱신, 문제 조회 중 상세를 보강하는 경로에도 같은 전체 저장이 있었다.

변경 전 실제 MongoDB에서 다음 순서를 고정해 실행했을 때 `최신 제목`이
`이전 제목`으로 돌아갔다.

```text
이전 Problem 조회
→ 같은 ID의 최신 메타데이터와 언어 저장
→ 이전 Problem을 바탕으로 상세 전체 저장
```

## 필드 갱신 범위

저장 작업마다 소유하는 필드를 분리했다.

| 작업 | 갱신 필드 | 보존 필드 |
| --- | --- | --- |
| solved.ac 메타데이터 | `title`, `category`, `difficulty`, `level`, `tags` | URL, 언어, 상세 |
| BOJ 상세 | 현재 상세 5개 | 메타데이터, URL, 언어, 레거시 상세 |
| 상세 새로고침 | 현재 상세 5개, 감지에 성공한 `language` | 나머지 필드 |
| 언어 갱신 | `language` | 메타데이터, URL, 상세 |

현재 상세 5개는 `descriptionHtml`, `inputDescriptionHtml`,
`outputDescriptionHtml`, `sampleInputs`, `sampleOutputs`다. 상세의 `null`과 빈
목록은 크롤링 결과대로 저장한다. 감지한 언어가 `null`이면 현재 DB의 언어를
다시 쓰지 않고 그대로 둔다.

## 변경

### 상세·언어 전용 저장

`ProblemRepositoryCustom`에 두 부분 갱신을 추가했다.

- `updateDetails`: `_id`가 있는 문서에 상세 5개와 선택적 언어만 `$set`
- `updateLanguage`: `_id`가 있는 문서에 언어만 `$set`

상세 갱신은 `findAndModify(returnNew=true, upsert=false)`를 사용한다. 언어 갱신도
upsert하지 않고 일치한 문서가 있는지를 반환한다. 크롤링 도중 문제가 삭제됐으면
상세나 언어만으로 불완전한 문제 문서를 다시 만들지 않는다.

### 전체 저장 경로 제거

다음 여섯 경로의 `problemRepository.save(Problem)`을 없앴다.

1. 동기 상세 수집
2. 비동기 상세 수집
3. 상세 새로고침
4. 언어 일괄 갱신
5. DB miss 뒤 solved.ac 문제 생성
6. 조회 중 상세 보강

DB에 문제가 없을 때는 메타데이터를 upsert한 뒤 현재 문서를 다시 조회한다. 그 사이 다른
작업이 상세를 저장했다면 재조회한 상세를 사용해 같은 BOJ 페이지를 다시
크롤링하지 않는다.

### 삭제 경합 처리

사용자 조회 중 갱신 대상이 사라지면 내부 오류 대신 재시도 가능한
`RESOURCE_STATE_CONFLICT(409)`를 반환한다. 관리자 배치는 삭제된 대상을 실패
건수로 기록한다.

동기 수집은 크롤링 뒤 대상이 삭제돼도 BOJ 요청 간 지연을 유지한다. 저장 결과와
관계없이 이미 외부 요청을 한 항목이므로 다음 요청을 바로 보내지 않는다.

## 정합성 비교

- Before SHA: `920d5ac471d140e59e3ce22441614133121ec56c`
- After code SHA: `32aee6a5f51ba4687d34f10f3158ffa7491a31dc`
- MongoDB: `mongo:7.0.16`
- 실제 서비스 검증: 공개 동기 `collectDetailsBatch`

실제 MongoDB 테스트는 목록 조회 뒤 크롤러 응답 직전에 최신 메타데이터와 언어를
저장해 오래된 대상 객체가 사용되는 순서를 결정적으로 만들었다. 별도 sleep이나
스레드 실행 순서에 기대지 않았다.

| 확인 항목 | Before | After |
| --- | --- | --- |
| 늦은 상세 저장 뒤 최신 메타데이터 | 이전 제목으로 복귀 | 제목·분류·난이도·level·tags 보존 |
| 늦은 상세 저장 방식 | 전체 문서 교체 | 상세 5개만 `$set` |
| 감지 실패 시 언어 | 오래된 조회값을 다시 저장 | 현재 DB 값 보존 |
| 삭제된 ID의 상세·언어 갱신 | 전체 저장 시 재생성 가능 | 문서 생성 0건 |
| 문제당 상세 저장 연산 | 1회 | 1회 |

마지막 행처럼 MongoDB 저장 연산 수는 줄지 않는다. 이 단계의 결과는 응답 시간이나
처리량 개선이 아니라 오래된 전체 문서가 최신 필드를 덮어쓰는 경로를 제거한
정합성 개선이다.

## 테스트와 커버리지

전용 MongoDB·Redis 컨테이너에 연결해 `clean check`를 실행했다.

| 범위 | Phase 5A | Phase 5B |
| --- | ---: | ---: |
| 단위 테스트 | 684개 통과 | 695개 통과 |
| 통합 테스트 | 167개 중 159개 통과 | 172개 중 164개 통과 |
| 조건부 제외 | 8개 | 8개 |
| core-v1 Line | 85.69% | 85.88% |
| core-v1 Branch | 63.98% | 64.44% |
| core-v1 Class | 93.48% | 93.51% |
| full-v1 Line | 72.81% | 74.21% |
| full-v1 Branch | 54.70% | 55.96% |
| full-v1 Class | 80.63% | 81.25% |

새 단위 테스트는 여섯 저장 경로의 부분 갱신 호출, 삭제 경합의 409 응답과 배치
실패 집계, 재조회 뒤 중복 크롤링 방지와 호출 간격을 확인한다.

새 실제 MongoDB 테스트는 다음 계약을 확인한다.

- 공개 수집 경로에서 최신 메타데이터와 언어 보존
- 상세 `null`과 빈 목록 저장
- 메타데이터·언어와 대표 레거시 필드 보존
- 부분 갱신 결과로 최신 문서 반환
- 삭제된 ID를 upsert하지 않음

커버리지 변화는 테스트 범위이며 성능 개선 수치로 사용하지 않는다.

## 남은 제한

- 실제 MongoDB 경합 테스트는 공개 동기 수집 경로를 검증한다. 비동기 작업의
  부분 갱신과 실패 집계는 단위 테스트로 확인했으며 실제 대기열 경합 수치로
  표현하지 않는다.
- update 명령 수가 같으므로 지연 시간이나 처리량 개선율을 주장하지 않는다.
- 기존 문제 문서에서 누락된 URL·언어와 과거 고아 문서의 수는 별도 dry-run으로
  확인해야 한다.
- 실제 BOJ·solved.ac 네트워크 호출과 EC2 배포는 검증 범위에서 제외했다.

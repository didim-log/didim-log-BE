# 관리자 회원 정렬 인덱스

관리자 회원 목록의 기본 정렬 `rating DESC, _id ASC`에 맞는 인덱스를 추가했습니다. 페이지 조회가 회원 전체를 검사하고 메모리에서 정렬하던 것이, 인덱스 순서대로 필요한 20명만 읽습니다.

## 이전과 현재

| 회원 1,000명, 20명 페이지 | 이전 | 현재 |
| --- | --- | --- |
| 페이지 조회 실행 계획 | `COLLSCAN` + 메모리 정렬(`SORT`) | `IXSCAN`, 메모리 정렬 없음 |
| 페이지 조회가 검사한 문서 | 1,000 | 20 (98.0% 감소) |
| 페이지 + 개수 조회가 검사한 문서 | 2,000 | 1,020 (49.0% 감소) |
| 깊은 페이지(skip 500)가 검사한 인덱스 키 | 0 | 520 |
| MongoDB 조회 | 3 | 3 |
| 응답 내용 | - | 이전과 같음 |

로컬 MongoDB 7.0.16에서 새 컨테이너로 5회 반복했고 결과가 모두 같았습니다. 관리자 조회가 실제로 보낸 명령을 `explain("executionStats")`로 측정한 검사 문서 수이며, 응답 시간이나 DB 비용 전체가 줄었다는 뜻은 아닙니다.

## 문제

[DB 페이징](./PHASE_1C_ADMIN_DB_PAGINATION.md) 뒤에도 `students`에는 `_id` 인덱스만 있어, 기본 목록을 볼 때마다 전체 회원을 검사하고 메모리에서 정렬했습니다.

## 바꾼 내용

앱 시작 때 `MongoIndexInitializer`가 다음 인덱스를 멱등적으로 만듭니다.

```text
collection: students
name: admin_rating_desc_id_asc
key: { rating: -1, _id: 1 }
```

- 리포지토리가 `rating DESC` 뒤에 `_id ASC`를 붙이므로 두 필드와 방향을 그대로 가진 복합 인덱스를 골랐습니다.
- 회고 인덱스와 회원 인덱스를 따로 확인해, 한쪽이 이미 있어도 다른 쪽이 빠지면 만듭니다. 기존 코드는 회고 인덱스가 있으면 바로 끝나서 회원 인덱스를 놓칠 수 있었습니다.
- 이름이 달라도 키·옵션이 같은 인덱스는 재사용합니다. 같은 인덱스가 hidden 상태면 임의로 바꾸지 않고 시작을 실패시킵니다.
- 가입일과 부분 문자열 검색 인덱스는 추가하지 않았습니다. 기본 정렬과 함께 쓰기 어렵고, 세 필드 부분 검색은 일반 B-tree 인덱스로 줄일 수 없기 때문입니다.

## 확인한 방법

- 실제 인덱스 목록과 옵션(non-unique, non-sparse, partial filter 없음, 기본 collation, visible)을 확인합니다.
- 단일 `rating` 인덱스나 다른 collation 인덱스가 있어도 복합 인덱스를 만드는지 확인합니다.
- 페이지 크기 1·5·10과 skip 500에서 인덱스 선택, 응답, 정렬, 명령 수를 확인합니다.
- `./gradlew clean check`가 통과했습니다(단위 485개, 통합 53개 중 46개 통과·조건부 7개 제외).

## 남은 한계

- 개수 조회는 여전히 `COLLSCAN`으로 1,000개를 검사하고, 깊은 페이지는 skip한 만큼 인덱스 키를 읽습니다.
- 인덱스만큼 저장 공간과 rating 갱신 비용이 늘어납니다. 큰 운영 컬렉션에서는 시작 시 인덱스 생성 시간을 따로 확인해야 합니다.
- 가입일 필터 인덱스, 부분 문자열 검색, 페이지 크기 상한은 정하지 않았습니다.

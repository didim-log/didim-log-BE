# Phase 6B — 유지보수 설정 원자화

## 문제

유지보수 설정은 Redis의 네 키에 나뉘어 있었다.

```text
maintenance:enabled
maintenance:startTime
maintenance:endTime
maintenance:noticeId
```

종료 시각 키에만 TTL이 설정돼 시간이 지나면 `endTime`은 사라지지만
`enabled=true`는 남을 수 있었다. 이 상태는 종료 시각이 없는 활성 설정처럼
해석돼 점검이 끝난 뒤에도 일반 요청을 계속 막았다.

설정과 조회도 여러 Redis 명령으로 처리했다. 동시에 두 관리자가 값을 바꾸면 한
요청의 시작 시각과 다른 요청의 공지 ID를 함께 읽을 수 있었고, 만료를 확인한 조회
요청이 비활성화를 위해 키를 지우는 사이 새 설정이 저장되면 그 설정까지 지울 수
있었다.

## 변경

### 설정과 TTL을 한 키에 저장

활성 여부, 시작·종료 시각과 공지 ID를 JSON으로 묶어
`maintenance:config`에 저장한다.

- 종료 시각이 있으면 `SET ... PX`로 설정 본문과 TTL을 함께 기록
- 종료 시각이 없으면 TTL 없는 `SET`으로 기록
- 비활성화하거나 이미 지난 종료 시각을 받으면 유지보수 키 전체 삭제

활성 설정 저장은 Lua 한 번으로 새 키를 기록하고 기존 네 키를 삭제한다. 새 설정이
만료된 뒤 기존 `enabled=true`가 다시 드러나는 경로를 막는다. 유한 설정을 무기한
설정으로 덮어쓸 때도 새 `SET`이 기존 TTL을 제거한다.

### 한 시점의 설정 조회

조회는 새 키와 기존 네 키를 한 번의 `MGET`으로 가져온다. 새 키가 있으면 항상 새
설정을 사용하고, 손상됐거나 비활성·만료된 새 설정을 기존 값으로 대체하지 않는다.
따라서 저장 전후의 필드가 섞이지 않는다.

만료된 본문을 읽더라도 조회 경로에서는 Redis 키를 삭제하지 않는다. Redis TTL이
정상 만료를 맡고, 조회 시각과 관리자 갱신이 겹쳐 새 설정을 지우는 일을 피한다.
알 수 없는 JSON 필드는 무시해 이후 설정 필드가 추가돼도 현재 필드를 계속 읽는다.

### 기존 네 키와의 전환

새 키가 아직 없으면 기존 `enabled`가 정확히 `true`인 설정을 읽는다. 시작·종료
시각은 파싱 가능한 값만 사용하고, 종료 시각이 이미 지났으면 비활성으로 응답한다.
조회 중 기존 값을 새 형식으로 옮기지는 않는다. 다음 관리자 쓰기에서 새 설정 저장과
기존 키 삭제를 함께 처리한다.

기존 데이터에서 `enabled=true`이고 `endTime`이 없으면 다음 두 상태를 값만으로
구분할 수 없다.

- 원래 종료 시각 없이 활성화한 설정
- `endTime`의 TTL만 만료되고 `enabled=true`가 남은 설정

기존 무기한 설정을 임의로 해제하지 않도록 전환 조회에서는 둘 다 무기한 활성으로
해석한다. 운영 전환 전에는 이 조합을 직접 확인해야 한다.

## 정확성 검증

Redis `7.2.5`의 전용 논리 DB에서 다음 경계를 확인했다.

| 검증 | 결과 |
| --- | --- |
| 종료 시각이 있는 설정 | 저장 직후 키 존재·활성·양수 TTL, 종료 뒤 키 없음·TTL `-2`·비활성 |
| 유한 설정을 무기한 설정으로 변경 | 양수 TTL이 `-1`로 바뀌고 새 설정 본문 유지 |
| 기존 네 키 조회 | 새 키가 없을 때 미래 종료 시각·공지 ID를 그대로 반환 |
| 기존 값 교체 | 새 설정 저장과 함께 기존 네 키 제거, 새 키 만료 뒤 재활성화 없음 |
| 비활성화 | 새 키와 기존 네 키 모두 제거 |
| 두 서비스의 동시 설정 | 두 설정 모두 조회에서 관측, 서로 다른 요청의 필드 조합 0건 |

동시성 테스트는 두 writer와 두 reader가 모두 준비된 뒤 함께 시작한다. 각 writer는
자기 설정이 실제 reader에 보일 때까지 저장을 반복하고, reader는 두 writer가 끝날
때까지 조회한다. 결과는 완전한 두 설정 중 하나로만 제한한다.

단위 테스트는 JSON 호환, 손상·만료 설정, 기존 키 우선순위와 쓰기 명령 경계를
확인한다. 통합 테스트는 실제 Redis에서 TTL, 기존 키 정리와 동시 설정을 확인한다.
전체 검증은 전용 MongoDB·Redis에 연결한 `clean check`로 실행한다. 이 단계는
정확성 검증이며 응답 시간이나 처리량의 개선율을 측정하지 않았다.

## 남은 제한

- 기존 `enabled=true`, `endTime` 없음 조합은 자동 판별할 수 없어 운영 전환 전에
  확인해야 한다.
- Lua와 `MGET`은 현재 단일 Redis 구성을 기준으로 한다. Redis Cluster로 옮기면
  유지보수 키가 같은 hash slot을 사용하도록 키 규칙을 먼저 바꿔야 한다.
- 구 버전은 새 `maintenance:config`를 읽지 못한다. 구·신 버전을 함께 실행하는
  순차 배포와 구 버전으로의 롤백은 별도 이중 쓰기 절차가 필요하다.
- EC2 배포와 운영 Redis 데이터 전환은 이번 검증 범위에서 제외했다.

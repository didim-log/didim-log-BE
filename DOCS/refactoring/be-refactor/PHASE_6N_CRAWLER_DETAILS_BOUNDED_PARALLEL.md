# 문제 상세 제한 병렬 수집

상세 수집에서 외부 조회만 최대 K개까지 동시에 하고, 저장과 진행률 갱신은 원래 순서대로 한 곳에서 하도록 바꿨습니다.

## 이전과 현재

| 항목 | 이전(순차) | 현재(`K=4`) |
| --- | ---: | ---: |
| 3,400건 처리 시간, 3회 중앙값 | 55.632초 | 12.226초 (77.96% 단축) |
| 누락·중복·미완성 상세 | 0건 | 0건 |
| 외부 조회 호출 | 3,400회 | 3,400회 |
| 저장·checkpoint 순서 | 대상 순서 | 대상 순서 (뒤 문제가 먼저 끝나도 동일) |
| 최대 동시 조회 | 1 | 4 |

실제 BOJ가 아니라 10ms 뒤 고정 응답을 주는 가짜 crawler로 외부 대기를 흉내 냈고, MongoDB 7.0.16·Redis 7.2.5와 저장·상태 갱신은 실제 코드를 썼습니다. 요청 간격 대기도 꺼 둔 조건이므로, 실제 BOJ 3,400건 수집 시간으로 읽으면 안 됩니다.

## 문제

상세 수집은 외부 응답을 기다리고, MongoDB와 Redis를 갱신한 뒤에야 다음 문제로 넘어갔습니다. 응답을 기다리는 동안 다른 문제를 준비할 수 없어서 건수만큼 대기 시간이 쌓였습니다.

그렇다고 끝난 순서대로 저장하면 진행률 규칙이 깨집니다. 처리 수는 정확히 1씩 늘고, checkpoint는 대상 목록에서 앞에서부터 연속으로 처리한 위치를 가리켜야 합니다. 느린 앞 문제보다 뒤 문제의 checkpoint를 먼저 저장하면, 재시작 뒤 그 사이 문제가 빠질 수 있습니다.

## 바꾼 내용

```mermaid
flowchart LR
    A["대상 목록"] --> B["요청 시작 간격 확보"]
    B --> C["최대 K개 동시 조회"]
    C --> D["대상 순서대로 결과 받기"]
    D --> E["MongoDB 부분 갱신"]
    E --> F["Redis 진행률·checkpoint 갱신"]
```

- 외부 조회와 대기만 전용 executor에서 실행합니다([`ParallelProblemDetailsFetcher`](../../../src/main/kotlin/com/didimlog/problem/application/collector/ParallelProblemDetailsFetcher.kt)).
- 결과는 끝난 순서와 상관없이 대상 순서대로 받아서, 저장과 상태 갱신을 한 곳에서 처리합니다.
- 동시에 들고 있는 결과는 최대 K개라 추가 메모리도 K개 분량입니다.
- 작업이 중단되면 기다리던 조회를 모두 취소하고 checkpoint를 옮기지 않습니다.
- 요청 간격은 요청이 끝난 뒤가 아니라 시작 직전에 적용하고, 같은 서버의 여러 수집 작업이 하나의 간격을 공유합니다. BOJ 상세는 2~4초 간격을 유지합니다.

```yaml
app:
  problem-collector:
    parallel:
      enabled: false
      max-concurrency: 1
```

동시성은 1~16으로 제한하고, 운영 기본값은 병렬 처리를 끈 상태입니다.

## 확인한 방법

| 조건 | 결과 |
| --- | --- |
| 1번이 느리고 2·3번이 먼저 끝남 | 저장과 checkpoint는 1, 2, 3 순서 |
| 중간 항목 조회 실패 | 실패 ID만 기록, checkpoint는 계속 진행 |
| 취소 뒤 남은 결과 도착 | 저장·진행률 증가 0건 |
| 작업 중단 | 남은 조회 취소, checkpoint 증가 0건 |
| `K=2`, `K=3` | 설정보다 많이 동시에 실행된 경우 0건 |

3,400건 측정은 세 번 모두 최종 문서 3,400건, 중복 호출 0회, 처리·성공 3,400건, 실패 0건이었고 순차와 병렬의 최종 결과가 같았습니다.

```bash
ALLOW_DIRTY_CRAWLER_DETAILS_BENCHMARK=true \
  performance/crawler/run-details-parallel-benchmark.sh
```

## 남은 한계

- 요청 간격은 서버 하나 안에서만 공유합니다. 여러 서버의 합산 요청률을 제한하려면 수집 worker를 하나로 두거나 Redis 기반 제한이 필요합니다.
- 취소해도 이미 시작한 최대 K개 요청을 바로 끊지는 않습니다.
- 429·5xx·timeout과 4xx를 구분한 자동 재시도는 아직 없습니다. 실패 ID를 남겨 재시도 API로 다시 수집합니다.
- 운영에서는 병렬 처리를 켜지 않았습니다. 켜기 전에 외부 사이트가 허용하는 요청률을 먼저 확인해야 합니다.

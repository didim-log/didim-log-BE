# Phase 3A — 풀이 결과 부분 갱신과 충돌 재시도

## 문제

풀이 결과 제출은 학생 문서를 읽어 `solutions`, 연속 풀이 일수와 마지막 풀이 날짜를
계산한 뒤 `Student` 전체를 저장했다. `documentVersion` 낙관적 잠금이 오래된 문서의
덮어쓰기는 막았지만, 같은 학생이 서로 다른 문제를 동시에 제출하면 먼저 저장한 요청만
성공하고 다른 요청은 409로 끝났다.

저장 뒤 Controller가 응답을 만들기 위해 같은 학생을 다시 조회하므로, 충돌이 없는
정상 경로에서도 MongoDB 명령이 하나 더 필요했다.

## 변경

풀이 상태에 필요한 세 필드만 `documentVersion` 조건으로 갱신한다.

```text
학생·문제 확인
→ 요청 제출 시각 고정
→ 현재 Student에서 풀이 상태 계산
→ _id + documentVersion 조건의 findAndModify
   $set solutions, consecutiveSolveDays, lastSolvedAt
   $inc documentVersion
→ 충돌이면 최신 Student를 읽고 다시 계산
→ 최초 1회 + 최대 3회 재시도 뒤에도 충돌하면 409
```

- CAS가 성공하면 `findAndModify(returnNew=true)`가 반환한 `Student`를 응답에 사용한다.
- 충돌을 뜻하는 CAS 결과 `null`만 재시도한다. MongoDB 연결 오류와 입력 오류는
  재시도하지 않는다.
- 재시도마다 최신 `solutions`를 기준으로 다시 계산하므로 다른 문제의 동시 제출 결과를
  보존한다.
- 같은 문제를 같은 날 다시 제출하면 `solvedAt`이 더 늦은 요청만 해당 날짜의 기록을
  교체한다. 먼저 시작한 요청의 재시도가 최신 제출을 과거 값으로 되돌리지 않는다.
- `solvedAt`은 요청마다 한 번 생성한다. 재시도 중 시각이 달라지거나 자정 경계에서
  풀이 날짜와 저장 시각이 어긋나지 않는다. MongoDB 저장 정밀도에 맞춰 밀리초로
  정규화하고 같은 시각이면 먼저 저장된 기록을 유지한다.
- 늦게 처리된 과거 제출은 풀이 배열을 시각순으로 다시 정렬하고, 마지막 풀이 날짜와
  연속 풀이 일수를 뒤로 돌리지 않는다. 과거 제출이 날짜 사이의 공백을 채우면 저장된
  풀이 날짜를 기준으로 연속 일수를 보완한다.
- CAS를 모두 소진하면 기존 `RESOURCE_STATE_CONFLICT`를 사용해
  `409`, `retryable=true`를 반환한다.

정상 제출의 MongoDB 명령 수는 다음과 같이 달라졌다.

| 경로 | Before | After |
| --- | ---: | ---: |
| 학생 조회 | 1 | 1 |
| 문제 조회 | 1 | 1 |
| 풀이 저장 | 1 | 1 |
| 응답용 학생 재조회 | 1 | 0 |
| 합계 | 4 | 3 |

이 표는 코드 경로의 명령 수 비교다. 지연 시간과 처리량은 반복 측정하지 않았으므로
성능 향상률로 환산하지 않는다.

## 검증

MongoDB 7.0.16을 별도 로컬 컨테이너로 실행했다.

- 같은 학생과 같은 문서 버전에서 서로 다른 문제 2건 동시 제출
  - 요청 오류 0건
  - 최종 풀이 기록 2건
  - `documentVersion` 2회 증가
  - 연속 풀이 일수 1회 반영
- 같은 문제를 같은 날 2건 동시 제출
  - 요청 오류 0건
  - 최종 당일 풀이 기록 1건
  - 최종 저장 시각은 두 응답의 저장 시각 중 최댓값
- 학생 조회 직후 비밀번호 부분 갱신을 실행한 뒤 풀이 제출
  - 첫 풀이 CAS 충돌
  - 최신 학생 재조회 후 풀이 저장
  - 새 비밀번호와 `credentialVersion` 보존
- 단위 테스트에서 첫 CAS 성공, 충돌 뒤 재계산, 4회 CAS 실패, 저장소 오류 비재시도,
  학생·문제 404를 확인했다.
- 먼저 시작한 요청의 재시도가 더 늦은 같은 문제 제출과 마지막 풀이 날짜를 되돌리지
  않고, 풀이 배열을 시각순으로 유지하는지 확인했다.
- 나노초가 다르지만 같은 밀리초로 저장되는 두 제출은 먼저 저장된 기록을 유지하는지
  확인했다.
- Controller 검증 실패는 400으로 고정하고, 서비스가 반환한 Student를 응답에 바로
  사용하는지 확인했다.

갱신하지 않았다.

## 남은 범위

- `solutions`는 학생 문서의 내장 배열이므로 풀이 필드 부분 갱신에서도 배열 전체를
  다시 쓴다. 배열 크기별 저장 비용은 별도 부하 측정이 필요하다.
- 계속해서 같은 학생 문서가 바뀌면 최초 시도와 최대 3회 재시도를 모두 소진해 409가
  발생할 수 있다.
- 회고 저장·북마크 토글·삭제는 별도 문서를 갱신한다. 회고와 풀이 기록 사이의
  원자성은 다음 회고 정합성 단계에서 다룬다.
- 이 단계는 동시 제출의 정합성과 정상 경로의 명령 수를 검증했다. 운영 처리량이나
  지연 시간 개선 수치는 기록하지 않는다.

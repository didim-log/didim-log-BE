# 풀이 결과 부분 갱신과 충돌 재시도

풀이 결과를 제출할 때 학생 문서 전체를 저장하던 것을, 풀이 관련 세 필드만 버전 조건으로 갱신하고 충돌하면 최신 값으로 다시 계산하도록 바꿨습니다.

## 이전과 현재

| 상황 | 이전 | 현재 |
| --- | --- | --- |
| 같은 학생이 서로 다른 문제 2건을 동시에 제출 | 1건 성공, 1건 409 | 2건 모두 저장, 오류 0건 |
| 같은 문제를 같은 날 2건 동시에 제출 | - | 당일 기록 1건, 더 늦은 제출 시각으로 저장 |
| 학생 조회 직후 비밀번호가 바뀜 | 전체 저장이 충돌 | 최신 문서로 다시 계산해 저장, 새 비밀번호 유지 |
| 정상 제출의 MongoDB 명령 | 4회 | 3회 (응답용 재조회 제거) |

로컬 MongoDB 7.0.16 컨테이너에서 확인했습니다. 명령 수는 코드 경로 비교이며 응답 시간은 재지 않았습니다.

## 문제

풀이 제출은 학생 문서를 읽고 풀이 목록, 연속 풀이 일수, 마지막 풀이 날짜를 계산한 뒤 `Student` 전체를 저장했습니다. `documentVersion` 낙관적 잠금이 오래된 문서의 덮어쓰기는 막았지만, 같은 학생이 다른 문제를 동시에 제출하면 먼저 저장한 요청만 성공하고 나머지는 409로 끝났습니다. 저장 뒤에는 응답을 만들려고 같은 학생을 한 번 더 조회했습니다.

## 바꾼 내용

```text
학생·문제 확인 → 제출 시각 고정 → 현재 문서로 풀이 상태 계산
→ _id + documentVersion 조건으로 findAndModify
   ($set 풀이 목록·연속 일수·마지막 풀이일, $inc documentVersion)
→ 충돌이면 최신 문서를 읽고 다시 계산 (최대 3회 재시도)
→ 그래도 충돌하면 409, retryable=true
```

- 갱신 결과 문서(`returnNew=true`)를 그대로 응답에 써서 재조회를 없앴습니다.
- 버전 충돌일 때만 재시도하고, 연결 오류나 입력 오류는 재시도하지 않습니다.
- 재시도할 때마다 최신 풀이 목록으로 다시 계산하므로 다른 문제의 동시 제출이 보존됩니다.
- 제출 시각은 요청마다 한 번만 정하고 밀리초로 맞춥니다. 같은 문제를 같은 날 다시 내면 더 늦은 제출만 그날 기록을 바꿉니다.
- 늦게 처리된 과거 제출은 목록을 시각순으로 정렬하고, 마지막 풀이일과 연속 일수를 뒤로 돌리지 않습니다.

## 확인한 방법

- 실제 MongoDB에서 위 세 가지 동시 상황을 재현했습니다. 다른 문제 2건 제출은 기록 2건, 버전 2회 증가, 연속 일수 1회 반영이었습니다.
- 단위 테스트로 첫 시도 성공, 충돌 뒤 재계산, 4회 실패 시 409, 저장소 오류 비재시도, 학생·문제 404를 확인합니다.
- 전용 MongoDB·Redis에 연결한 `./gradlew clean check`가 통과했습니다(단위 639개, 통합 139개 중 132개 통과·조건부 7개 제외).

## 남은 한계

- 풀이 목록은 학생 문서 안의 배열이라 부분 갱신이어도 배열 전체를 다시 씁니다.
- 같은 학생 문서가 계속 바뀌면 재시도를 다 써서 409가 날 수 있습니다.
- 회고와 풀이 기록 사이의 정합성은 [회고 원자 갱신과 풀이 기록 삭제 정합성](./PHASE_3B_RETROSPECTIVE_ATOMIC_UPDATES.md)에서 다뤘습니다.

# Gemini 호출 제한 원자화

Gemini 호출 제한(최소 간격, 분당·일일 한도)의 검사와 기록을 Redis Lua 한 번으로 묶었습니다. 동시에 들어온 요청이 한도를 넘지 않고, 429 재시도도 매번 허가를 다시 받습니다.

## 이전과 현재

| 같은 시각 20건 동시 요청 (최소 간격 4초) | 이전 | 현재 |
| --- | ---: | ---: |
| 허용 | 15건 | 1건 |
| 분당 사용량(RPM) 기록 | 20 | 1 |
| 일일 사용량(RPD) 기록 | 15 | 1 |

| 상황 | 이전 | 현재 |
| --- | --- | --- |
| 차단된 요청 | RPM만 올라가고 RPD는 안 올라감 | 어느 카운터도 올리지 않음 |
| 429 뒤 재시도 | 허가 없이 다음 HTTP 요청 | 재시도마다 허가 확인, 거절되면 요청하지 않음 |
| Redis 장애 | - | 공급자 호출 0건, 503 |

로컬 Redis 7.2.5에서 같은 동시성 테스트를 이전·현재 코드에 돌린 결과입니다. 이전 코드는 "1건만 허용" 검사가 `expected: 1, actual: 15`로 실패했습니다. 응답 시간이나 처리량은 재지 않았습니다.

## 문제

`GeminiRateLimiter`는 최소 간격, RPM, RPD를 각각 다른 Redis 명령으로 처리했습니다.

```text
GET last → INCR rpm (+EXPIRE) → INCR rpd (+EXPIRE) → SET last
```

같은 순간에 온 요청들은 `last`를 함께 읽고 모두 최소 간격 검사를 통과했습니다. RPM은 올린 뒤에 한도를 확인해서 차단된 요청까지 RPM에 들어갔고, 그 요청은 RPD와 `last`를 남기지 않았습니다.

429 재시도는 첫 요청 전에 받은 허가 하나로 다음 HTTP 요청까지 보냈습니다. 실제 공급자 요청 수와 Redis에 기록된 허가 수가 달라질 수 있었습니다.

## 바꾼 내용

### 검사와 기록을 한 번에

서버는 현재 UTC 분·일 키와 남은 시간, 정책값을 Lua 스크립트에 넘기고, 스크립트가 아래를 한 번에 처리합니다.

```text
세 값 읽기 → 값 검증 → 최소 간격, RPM, RPD 순서로 한도 확인 → 허용된 요청만 기록
```

| 결과 | 의미 | 카운터 |
| --- | --- | --- |
| 허용 | 세 조건 모두 통과 | RPM·RPD 1씩 증가 |
| 최소 간격 미달 / RPM 한도 / RPD 한도 | 차단 | 변경 없음 |
| 저장값 손상 | 실패 | 변경 없음 |

정상 구간에서 4번, 새 분·일의 첫 요청에서 최대 6번이던 Redis 왕복이 1번으로 줄었습니다.

키 이름은 기존과 같아서 별도 변환 없이 이어 씁니다. 이전 코드가 남긴 만료 없는 키는 처음 읽을 때 남은 시간에 맞춰 만료를 설정하고, 숫자가 아니거나 음수인 값은 허용하지 않습니다.

### 재시도마다 허가 받기

허가 확인과 HTTP 요청을 `Mono.defer`로 묶어, 첫 요청과 429 뒤 재요청이 모두 같은 순서를 따릅니다.

```text
허가 받기 → Gemini 요청 → 429면 대기 → 허가 다시 받기 → 다음 요청
```

대기 시간은 backoff와 최소 간격 중 긴 쪽입니다. 429가 계속되면 `AI_SERVICE_BUSY`를, Redis 연결 실패나 시간 초과면 `RATE_LIMIT_SERVICE_UNAVAILABLE`(503)을 돌려주고, AI 리뷰 작업은 실패로 기록하면서 미리 예약한 사용량을 돌려놓습니다.

| 설정 | 기본값 | 환경 변수 |
| --- | ---: | --- |
| 최소 호출 간격 | 4초 | `GEMINI_RATE_LIMIT_MIN_INTERVAL_SECONDS` |
| 분당 한도 | 15 | `GEMINI_RATE_LIMIT_MAX_RPM` |
| 일일 한도 | 1,500 | `GEMINI_RATE_LIMIT_MAX_RPD` |

## 확인한 방법

실제 Redis 통합 테스트 9개에서 확인했습니다.

- 같은 시각 20건 중 1건만 허용, RPM·RPD 각 1 기록
- RPM이 14일 때 20건 중 1건만 허용, 최종 RPM 15
- 차단 시 카운터와 만료 시간을 늘리지 않음
- 이전 키 자동 전환, 손상된 값 거절, UTC 분·일 경계 전환

로컬 HTTP 서버로 재시도도 확인했습니다.

- `429` 뒤 `200`이면 HTTP 요청 2건과 허가 2건이 일치
- 두 번째 허가가 거절되면 HTTP 요청은 1건에서 멈춤
- Redis가 멈추면 공급자 요청 0건, 503

```bash
./gradlew test --tests '*GeminiRateLimiterTest' --tests '*GeminiLlmClientRetryTest' \
  --tests '*AiReviewServiceTest' \
  integrationTest --tests '*GeminiRateLimiterIntegrationTest'
```

## 남은 한계

- 이전 버전은 같은 키를 개별 명령으로 바꾸므로 섞어 돌리지 않고 한 번에 교체해야 합니다.
- 분·일 구간은 각 서버의 UTC 시각으로 계산하므로 서버와 Redis의 시간 동기화가 필요합니다.
- 세 키에 hash tag가 없어서 단일 Redis 기준입니다.
- 허가 뒤 네트워크 실패나 429가 나도 이미 시도한 호출은 사용량에 남깁니다. 공급자 요청을 보수적으로 세기 위한 정책입니다.
- 실제 Gemini 계정 한도와 운영 Redis 전환은 확인하지 않았습니다.
